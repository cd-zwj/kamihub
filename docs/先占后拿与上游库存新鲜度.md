# 先占后拿 + 上游库存新鲜度（本次改造说明）

## 一、为什么要「先占后拿」

匿名购买是 `邮箱+密码 → 创建支付单 → 支付宝付款 → 回调自动下单取卡`。
从点「去支付」到回调到账，中间隔着**几分钟**，而这段时间里卡密一直是
`available` —— 别的买家（尤其秒下的登录买家）会把它买走，于是匿名买家
付款成功却收到「商品暂时缺货」，钱退进余额。

现在的口径：**创建支付单时就把卡密锁成 `held`**，付款成功后直接转 `sold`，
付款超时/失败由定时任务退回 `available`。窗口从「几分钟」压到「几毫秒」。

### 关键实现

| 位置 | 作用 |
| --- | --- |
| `card_stocks.status = 3 (held)` + `held_by_request` + `hold_expires_at` | 预占的数据载体 |
| `CardService.ReserveForPayment` | 创建支付单时逐张原子占用（`FOR UPDATE SKIP LOCKED`），占不满整批回滚 |
| `CardService.TakeHeld` | 付款成功后把预占直接转 sold 并绑订单号，不给别人抢的窗口 |
| `CardService.ReleaseHold` | 支付失败/下单失败/支付单落库失败，立刻退回可售 |
| `CardService.SweepExpiredHolds` | 定时清理过期预占（买家点了去支付又关页面） |
| `PaymentService.CreatePay` | 落库支付单**之前**预占；占不到当场拒绝，绝不收钱 |
| `ShopOrderService.Purchase` | 报价时把「自己占的张数」加回可售；下单失败时释放预占 |
| `OrderService.deliverFromPool` | 发卡时**先吃预占**，不够再 `TakeOne` 补 |

**为什么不需要改各处库存口径**：`CountAvailable` 只数 `status = available`，
预占天然被排除 —— 商城展示、混合模式取货计划、下单前校验自动全部正确。
唯一要补的是「占它的那个人自己」，见 `BuyerQuoteForWithReserved`。

## 二、为什么要修「上游没货了还显示有货」

库存是缓存，靠定时任务刷新（默认 2 分钟）。但同步会因为上游抖动、
平台被禁用、worker 没跑而失败，而失败时我们**刻意保留旧库存**
（避免一次抖动把已知库存清成 0）。副作用就是：上游早就没货，商城还挂着
「库存 5」，买家付完钱才退款。

两道修正：

1. **展示层不再相信过期数字**（`SupplyStockTTL = 15min`）
   `ShopListing.stock_stale = true` 时前端显示「库存待确认」，
   而不是继续挂「有货 N」。`isSoldOut` 也不会因为过期的 0 把商品判死。

2. **下单前强制实时询价**（`GoodsService.RefreshStaleSupplyStock`）
   `BuyerQuoteFor` 被「下单」和「创建支付单」共用，走这里时若发现该商品
   货源缓存过期，先向上游询一次价把缓存刷成真值，再决定卖不卖。
   商品列表/详情不进这条路径，不会被上游抖动拖慢。

## 三、上线步骤

```bash
cd backend && go build ./...        # 自检
docker compose up -d --build backend
```

`DB_AUTO_MIGRATE=true` 会自动加列（`card_stocks` 本来就在 AutoMigrate 列表里）。
若某环境关了自动迁移，手工执行：

```sql
-- 先占后拿
ALTER TABLE card_stocks ADD COLUMN IF NOT EXISTS held_by_request varchar(128);
ALTER TABLE card_stocks ADD COLUMN IF NOT EXISTS hold_expires_at timestamptz;
CREATE INDEX IF NOT EXISTS idx_card_stocks_held_by_request ON card_stocks(held_by_request);
CREATE INDEX IF NOT EXISTS idx_card_stocks_hold_expires_at ON card_stocks(hold_expires_at);

-- 自动发货单飞（上一批修复）
ALTER TABLE payment_orders ADD COLUMN IF NOT EXISTS auto_order_claim_at timestamptz;
ALTER TABLE payment_orders ADD COLUMN IF NOT EXISTS auto_order_attempts bigint NOT NULL DEFAULT 0;
CREATE INDEX IF NOT EXISTS idx_payment_orders_auto_order_claim_at ON payment_orders(auto_order_claim_at);
```

## 四、上线后验证

```sql
-- 1) 预占是否在工作：应看到少量 held，且都有过期时间
SELECT id, goods_id, held_by_request, hold_expires_at
FROM card_stocks WHERE status = 3 ORDER BY id DESC LIMIT 20;

-- 2) 预占是否卡死：过期了还没被清理（应为 0 行；有的话说明 worker 没跑）
SELECT count(*) FROM card_stocks
WHERE status = 3 AND hold_expires_at < now() - interval '5 minutes';

-- 3) 上游缓存新鲜度：这些货源的数字不可信，页面会显示「待确认」
SELECT id, goods_id, platform_id, platform_goods_no, stock, stock_synced_at
FROM supplies
WHERE enabled AND (stock_synced_at IS NULL OR stock_synced_at < now() - interval '15 minutes');
```

前端验证：把某个商品的卡池卖到只剩 1 张，用匿名通道下单但不支付，
回商城看该商品库存应减 1（预占生效）；支付超时后（hold TTL = 支付单 TTL + 10 分钟）
库存应恢复。

## 五、注意

- 预占 TTL = `支付单有效期 + 10 分钟`，与支付单生命周期对齐。
- 买家点了「去支付」但关掉页面，卡密最多被锁这么久，之后由
  `stockSyncTask`（默认 2 分钟一轮）清理。
- 后台卡密池统计新增 `held`（预占中），
  `Total = 可用 + 已售 + 作废 + 预占`。
