# 匿名购买「没货 / 余额不足」排查与修复

> 现象：买家（尤其匿名购买）付款成功后，页面提示
> 「商品暂时缺货，本次没有发货」或「平台备货账户余额不足，我们正在处理」，
> 但运营查上游明明有货、上游账户也有钱；有时过一会儿订单列表里又能看到已发货的订单。

## 一、这两句话是谁说的

它们不是库存判断，而是 `PaymentService.autoOrderFailHint()`
（`backend/internal/service/payment.go`）对 `payment_orders.auto_order_error` 的翻译。
也就是说：**买家看到的是「付款后自动下单失败」，不是「商品没货」。**

## 二、根因

### 1. 自动发货没有单飞，同一笔支付被并发跑两遍（主因）

`dispatchPaidOrder` 有三个触发点，且一定重叠：

| 入口 | 触发方式 |
| --- | --- |
| `HandleNotify` | 易支付异步回调，**上游会重复推送** |
| `HandleNotify` 的「重复通知」分支 | `handled=true` 之后仍然调用 dispatch |
| `settlePaid` | 买家每 5 秒轮询 → `QueryAndSettle` → 主动查单补入账 |

两路用**同一个** `PurchaseRequestID` 并发进 `ShopOrderService.Purchase`：

1. 先到者冻结余额、开始采购（`waitForDelivery` 阻塞几十秒）
2. 后到者读到「余额已被冻结」→ `ErrInsufficientFunds`（"余额不足"），
   或「流水已存在但订单未落库」→ "该请求正在处理中"
3. 失败分支把这句话写进 `auto_order_error`
4. 前端轮询看到 `attempted && !ok` → 立即停止轮询并显示失败

结果：**订单正在正常生成，买家却被告知没货 / 余额不足。**

### 2. 一次失败永久判死

`order_id IS NULL && auto_order_error != ''` 是「不再尝试」的闸门，
连网络抖动、上游限流、并发抢占这类秒级自愈的错误也一起判死。

### 3. 两种「余额不足」被混成一条

`wallet.ErrInsufficientFunds`（**买家钱包**）与
「平台余额不足：需要 x，可用 y」（**上游备货账户**）都落到同一条分支，
统一翻译成「平台备货账户余额不足」—— 把排查方向引到上游余额上。

### 4. 混合模式商品付款前不查库存

`BuyerQuoteFor` 原来只判 `IsLocalStock()`（仅 `stock_mode=2`），
`stock_mode=3`（混合）整段跳过 → 买家付完钱才在上游撞「已售罄」。
（本次已修，见 `listing.go` 与 `shop_order_test.go`）

## 三、修复内容

| 文件 | 改动 |
| --- | --- |
| `service/payment.go` | `claimAutoOrder`/`releaseAutoOrderClaim` 单飞锁；最多 3 次重试（换幂等键 `-r2/-r3`）；失败前回读 `order_id`；`markAutoOrder` 失败写入加 `order_id IS NULL`；`autoOrderFailHint` 拆分两种余额不足 |
| `models/buyer.go` | `PaymentOrder` 新增 `auto_order_claim_at`、`auto_order_attempts` |
| `service/listing.go` | 混合模式下单前库存校验（池子 + 上游缓存） |
| `service/guest.go` | 匿名买家查找先按 `is_guest=true` 过滤，已注册过正式账号的老客户不再被挡住 |
| `service/auto_order_dispatch_test.go` | 重试判定与文案分离的回归测试 |

## 五、巡检历史问题单

```sql
-- A. 假失败样本：付款成功、没发货、错误里带「余额不足 / 正在处理中」
SELECT id, trade_no, buyer_id, amount, auto_order_error, auto_order_at, created_at
FROM payment_orders
WHERE purpose = 'order' AND status = 'paid'
  AND order_id IS NULL
  AND (auto_order_error LIKE '%余额不足%' OR auto_order_error LIKE '%正在处理中%')
ORDER BY id DESC LIMIT 100;

-- B. 需要人工处理的真·未发货单（钱在买家余额里）
SELECT id, trade_no, buyer_id, listing_id, quantity, amount, auto_order_error, paid_at
FROM payment_orders
WHERE purpose = 'order' AND status = 'paid' AND order_id IS NULL
ORDER BY id DESC;

-- C. 同一笔支付被派发多次的痕迹
SELECT trade_no, notify_count, auto_order_at, auto_order_attempts, order_id, auto_order_error
FROM payment_orders
WHERE purpose = 'order' AND notify_count > 1
ORDER BY id DESC LIMIT 50;
```

## 六、上线后验证

1. 用匿名购买真实下一单，付款后观察 `docker logs -f kamihub-backend`：
   - 正常应看到一条 `直付购卡自动发货成功 ... attempt=1`
   - 并发被拦住时出现 `自动发货已由其它入口在处理，本次跳过`（这是期望行为）
   - 不应再出现同一 `trade_no` 的 `自动发货失败` + `auto_order_error`
2. 买家页面应直接显示卡密，或显示「支付已到账，正在自动发货，请稍候…」（而不是失败）。
3. 复核第五节 A 查询：新产生的单子里不应再出现「余额不足」类假失败。

## 七、已知残留（未在本次修改）

**卡密池是「先查后取」，没有预占。** `BuyerQuoteFor` 数一遍 `CountAvailable`，
真正 `TakeOne` 发生在付款之后。匿名买家付款窗口更长，最后一张被并发抢走就会出现
「付款成功 → 发货失败 → 商品暂时缺货」。彻底解法是在创建支付单时做库存预占
（`stock_holds` 表 + `expires_at` 超时释放），改动量较大，单独排期。

## 八、追记：页面写 10 元、收银台收 10.1 元、回调失败

### 现象

商品页/确认弹窗显示 ¥10，跳到收银台变成 ¥10.1，付款后回调被判金额不一致，
买家付了钱却不到账、不发货。

### 三个金额各说各话，根因是两处

1. **报价没带买家身份**（`shopQuoteListing` 走 `BuyerQuote` buyerID=0 = 零售价），
   而实际扣款走 `BuyerQuoteFor`（档位专价）。代理/销售买家看到 10、服务端记 9。
   线上日志实锤：`直付购卡前端金额与服务端不一致 client_amount=10 server_amount=9`。
2. **网关对同金额未支付单自动抬价**（10.00 → 10.10 这种），本身没有上限。
   而旧实现只容忍「多付 ≤ 0.10」，再加上上面的 1 元差价，差额 1.10 → 直接拒单，
   回调返回 fail，上游无限重试，钱卡在通道里。

### 修法

| 改动 | 说明 |
| --- | --- |
| 报价接口带身份 | 新增 `optionalBuyerID`，`shopQuoteListing` 用 `QuoteFor(..., buyerID)`，页面显示 = 服务端成交价 |
| 创建支付单带身份 | `CreatePay` 改用 `QuoteFor(ctx, listingID, qty, buyerID)`，支付金额与下单金额同源 |
| 金额判定 | `amountAcceptable` 改为**少付拒绝、多付一律放行**（多付对平台零风险） |
| 入账口径 | `HandleNotify` / `settlePaid` 按**买家实付金额**入账（多付的留在买家余额），账面不再缺口 |
| 前端提示 | 付款页写明「通道可能微调，多付部分自动退回余额」 |

### 为什么不干脆「把金额做成唯一值」

给每单加随机分（10.03、10.07）能绕开网关去重，但买家看到 9.5 元的商品付 10.07，
体验更差，还会让对账、发票、客诉全部变复杂。让通道抬、按实付入账，是代价最小的解。
