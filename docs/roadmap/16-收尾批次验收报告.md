## 二、风控命中接通知告警

### 2.1 设计：只对 reject 告警，review 只落库

这是刻意的分级：

| 级别 | 动作 | 理由 |
| --- | --- | --- |
| `reject` | 落库 + **推告警** | 有人被真的拦下来了。可能是黑产在试，也可能是我们规则配错在拦正常客户 —— 两种都必须有人看见 |
| `review` | 只落库 | 「有人被标记复核」不值得打扰。review 级命中量天生更大，每次都推会把人逼到关掉告警 |
| `pass` | 无 | 没命中 |

### 2.2 防刷屏靠现成的聚合窗口

新增事件常量 `notify.EventRiskRejected = "risk.rejected"`，复用 `Notifier.Alert` 已有的
「同一 event + 实体 5 分钟内只推一次」机制，**没有新写一套限流**。

风控命中在高峰期可能每分钟几十条，不聚合会直接把 Telegram 刷爆，
然后运维把告警关掉 —— 那这次改动就白做了。

### 2.3 注入方式：setter 而非构造参数

```go
riskSvc := service.NewRiskService(db, c).WithNotifier(notifier)
```

理由：风控的核心职责是「判不判」，告警是附加能力。
`notifier` 为 nil 时风控照样完整工作（只记录不推送），
所以不该因为它改变构造函数签名、波及所有调用方与测试。

### 2.4 告警内容

```
标题：风控拦截了一次注册
正文：主体 ip:127.0.0.1（IP 127.0.0.1）触发规则 blacklist_match
结构化字段：scene / subject / ip / rules / amount / buyer_id
链接：/admin/security（直接跳到「风险命中」页复核）
```

### 2.5 实测证据

用黑名单制造一次 reject 命中（把一个邮箱拉黑 → 用该邮箱注册）：

```
黑名单已加 id=9
注册被拒：403

     event     | level |       title
---------------+-------+---------------------
 risk.rejected | warn  | 风控拦截了一次注册
```

告警已落库（站内信可见）。若配了 Telegram / Webhook，同一时刻也会推送。

## 三、图表按需加载：首屏主包 −128.90 kB

### 3.1 做法

`Dashboard` 是唯一 import `recharts` 的页面。改成 `React.lazy` + `Suspense`：

```tsx
const Dashboard = lazy(() => import('@/pages/Dashboard'));
...
<Route path="/admin" element={<Suspense fallback={<FullScreenSpin />}><Dashboard /></Suspense>} />
```

首屏只加载登录页与布局，`recharts` 那一大坨在真正进入「概览」时才下载。

### 3.2 效果（实测，gzip）

| 版本 | 主包 | Dashboard chunk | 合计 |
| --- | --- | --- | --- |
| 引入 recharts 前 | 511.50 kB | — | 511.50 kB |
| 引入 recharts 后（单包） | **650.40 kB** | — | 650.40 kB |
| **懒加载后** | **521.50 kB** | 129.01 kB | 650.51 kB |

**首屏主包从 650.40 → 521.50 kB，减少 128.90 kB（−19.8%）**，
基本回到引入 recharts 之前的体量。

这直接回答了我上一轮报告里标的「首屏加载 < 2s 未实测」：
原来首屏必须下载 650 kB 才出第一个像素，现在只要 521 kB。

## 四、销售中心销量统计改折线图

### 4.1 为什么不用 recharts

`AgentCenter` 属于**商城侧**，如果它也 `import recharts`，
会把 recharts 重新拉回主包 —— 上一节的 128.90 kB 就白省了。

所以新增零依赖的 `components/Sparkline.tsx`：内联 SVG 折线/面积图，约 130 行。

**用对的工具，不是用最强的工具。** 「14 天销量趋势」只需要一条线，
没有 tooltip / 图例 / 缩放的需求。需要交互时才该上 recharts（见 `Dashboard.tsx`）。

### 4.2 呈现

销量统计 Tab 现在是「两张折线图 + 明细表格」：

```
近 14 天订单量   [面积折线，主色]
近 14 天金额     [面积折线，绿色]
────────────────────────────
明细表格（日期 / 订单数 / 金额）
```

X 轴只标首尾两个日期 —— 14 个日期全标会糊成一团，中间看表格。

空数据显示「暂无数据」占位，不会画出一条贴底的直线误导人。

## 五、移动端抽屉宽度自适应

### 5.1 抽 hook，不写 `window.innerWidth`

```ts
// src/hooks/useIsMobile.ts
export function useIsMobile(): boolean {
  const screens = Grid.useBreakpoint();   // 和 <Col xs/md> 同一套断点
  ...
}
export function useDrawerWidth(desktopWidth: number): number | string {
  return useIsMobile() ? '100%' : desktopWidth;
}
```

用 antd `Grid.useBreakpoint()` 而不是 `window.innerWidth` 的原因（也是 `05` 文档的要求）：
媒体查询断点与栅格系统一致、自动订阅 resize、不用每处自己监听并清理。

首帧 `screens` 为空对象时按「桌面版」处理 —— 宁可先渲染桌面再切窄，
也不要先渲染手机版再撑开（会闪一下）。

### 5.2 已适配的抽屉

| 页面 | 原宽度 | 现在 |
| --- | --- | --- |
| `Deliveries.tsx` 详情 | 640 | 手机 100% |
| `Goods.tsx` 货源管理 | 860 | 手机 100% |
| `Logs.tsx` 详情 | 680 | 手机 100% |
| `Orders.tsx` 订单详情 | 720 | 手机 100% |
| `ShopAdmin.tsx` 买家/上架详情 | 640 | 手机 100% |

加上上一批次已做的「19 处表格 `scroll={{x:'max-content'}}`」，
手机上「抽屉溢出 + 表格被裁」这两个最痛的问题都解决了。

**未做**：工具栏按钮收进「更多」下拉、表单两列在窄屏改单列。
这两项是锦上添花，且要逐个页面改，收益不如上面两项明显。
