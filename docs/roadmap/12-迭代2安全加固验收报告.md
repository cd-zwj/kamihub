## 二、关键设计决策（都是「为什么这么做」而不是「做了什么」）

### 2.1 2FA 为什么必须用「一次性临时票据」

最容易做错的实现是：密码通过后先签发一个「带 `totp_pending` 标记的登录令牌」，前端拿着它去换正式令牌。这样做 2FA 等于装饰 —— 攻击者拿到密码后，那个半成品令牌往往也能调不少接口。

本项目采用的设计：

```
密码正确 + 已开 2FA
  → 返回 { need_totp: true, ticket }，**没有 token**
  → ticket 的 JWT typ = "totp"
  → Auth 中间件的 IsStaffToken() 只认 ""/"staff"，直接拒绝
  → ticket 绑一个随机 nonce 写进 Redis，消费时 DEL（返回 0 = 已用过）→ 物理一次性
  → 5 分钟过期
```

验收脚本专门验了这一点：**临时票据调 `/api/auth/me` 返回 401**。

### 2.2 为什么 Setup 之后不能直接启用

`Setup` 只生成密钥并加密暂存，`totp_enabled` 仍为 false。必须走 `Confirm` 输入一次正确动态码才启用。

理由：如果扫码失败（手机不支持、时区错乱、Secret 抄错）却已经把账号标记为「已启用」，用户就再也登不进去了 —— 这是一个自锁死局，且只能靠改库恢复。

### 2.3 恢复码：只给一次、只存哈希、只能用一次

- 明文只在 `Confirm` 的响应里出现一次，之后任何人都取不到
- 库里只存 `SHA-256(规范化后的码)`。恢复码本身是 12 位高熵随机串，没有字典攻击面，所以不需要 bcrypt 那种慢哈希（否则每次验证要跑 10 次 bcrypt）
- 一次性靠**条件更新**保证：`UPDATE ... WHERE used_at IS NULL` 的 `RowsAffected` 就是并发下的仲裁结果
- 规范化容忍 `ABCD-EFGH-IJKL` / `abcdefghijkl` / 带空格等手抄变体

### 2.4 为什么「admin 未绑定 2FA」不硬拦

设计文档要求「强制引导」。本项目选择**引导 + 登录响应带 `totp_setup_required` + 后台黄条提醒**，而不是拒绝登录。

原因：硬拦会让「刚初始化、还没绑手机」的站长连后台都进不去，反而制造自锁死局。这是可用性与安全性的明确取舍，写在验收报告的偏差里。

### 2.5 验证码：为什么是算术题而不是图形码

图形码的防护力来自「识别难度」，而自研图形码的识别难度基本为零（随便一个 OCR 就破），却把无障碍和移动端体验搞坏。

选「算术题 + 一次性 + 失败封禁」：

- **成本不对称**：真人 3 秒；脚本要先理解题目语义（比 OCR 难得多）
- **一次性**：Redis `GETDEL` 原子取走答案，校验即销毁。这是把「一次性」做对的关键——用 `GET` 再 `DEL` 会有并发窗口
- **答错也销毁**：不允许「猜错再猜」，否则 3 位数字可以被在线爆破
- **失败封禁**：同一 captcha session 错 3 次封 15 分钟

### 2.6 风控：不做 DSL，只做「规则表 + 顺序评估」

kamihub 的量级用不着 Drools 那类引擎——上了只会让「改一条阈值」变成一次发版 + 一次回归。

这里 `Config` 是纯参数（窗口、上限、倍数、比例），判断逻辑固定在各规则的 Go 实现里。**能热改的正是最需要热改的东西**：开关、级别、优先级、阈值。

规则缓存 10 秒自然过期 + 管理端保存时主动 `Invalidate()`，所以：

- 单进程：立刻生效
- 多进程（api + worker）：最多 10 秒收敛

### 2.7 通配场景 `scene=all`：黑名单必须全场景生效

第一次实现时把黑名单规则设成了 `scene=order`，结果**注册时被拉黑的邮箱照样能注册**——这是冒烟脚本抓到的真实缺陷（见 §四）。

黑名单的本质是「这个人整体不可信」，不该只在某一种操作里被拦，否则换个入口就绕过去了。因此引入 `SceneAll`，`rulesFor()` 把「本场景规则 + 通配规则」合并后按 priority 排序。

### 2.8 风控挂了必须放行（可用性优先）

`Evaluate()` 在以下情况返回「放行 + 记 error 日志」：

- 规则读不出来（DB 异常）
- Redis 计数器拿不到（`bump` 返回 0）
- 命中记录写不进去

理由：风控是**减损**手段，不是**收款前置条件**。风控挂掉导致全站下不了单，损失远大于漏掉几条可疑订单。这个取舍必须显式写下来，否则下一个人会「顺手改成报错」。

## 三、8 条基础规则

| # | code | 场景 | 出厂阈值 | 判定 | 实现要点 |
| --- | --- | --- | --- | --- | --- |
| R1 | `ip_register_velocity` | register | 60 分钟 > 3 | review | Redis 计数，窗口首次自增时设 TTL |
| R2 | `ip_order_velocity` | order | 10 分钟 > 10 | review | 同上 |
| R3 | `buyer_order_velocity` | order | 60 分钟 > 20 | review | 同上 |
| R4 | `order_amount_anomaly` | order | 客单价 × 5 | review | 近 30 天 AVG 缓存 10 分钟；无数据时退回绝对阈值 `max_amount` |
| R5 | `daily_amount_anomaly` | order | 当日累计 > ¥2000 | review | 当日 `SUM(paid_amount)`，排除 failed |
| R6 | `refund_rate_anomaly` | order | 近 30 天 > 30% 且 ≥3 单 | **reject** | 分母是订单数，不是金额 |
| R7 | `blacklist_match` | **all** | 精确匹配 | **reject** | 支持 IP / 买家 / 邮箱；排除已过期条目 |
| R8 | `self_purchase` | commission | — | reject | **出厂关闭**：分销未上线，没有上下级关系可判 |

R4 的一个坑值得记录：如果直接用「客单价 × 倍数」，新站没有历史数据时 `avg = 0`，`limit = 0`，规则变成「永远不命中」——看似安全，实则完全失效。所以补了「无基线时退回绝对阈值」。

## 四、开发中发现并修掉的两个真实缺陷

### 缺陷 1：黑名单规则只在 order 场景生效

冒烟脚本报：

```
FAIL 命中黑名单的注册被拒  -- status=200 msg=success
```

原因：`RuleBlacklist` 的 `Scene` 写成了 `SceneOrder`，注册场景的 `rulesFor("register")` 拿不到它。

修法：
1. 新增 `models.SceneAll`，黑名单规则改为 `scene=all`
2. `rulesFor()` 合并「场景规则 + 通配规则」
3. `SeedDefaultRules` 增加「已存在规则只修正 scene」的分支 —— 老库里那条也得跟着改，否则升级后依然失效

### 缺陷 2：GORM 又一次把显式 `false` 吞成 `true`

`RiskRule.Enabled` 原本写 `gorm:"not null;default:true"`。于是出厂应为**关闭**的 `self_purchase` 规则被静默打开：

```
code                  | scene      | enabled
self_purchase         | commission | t      ← 应该是 f
```

这是本项目第二次踩同一个坑（第一次是 `Goods.LocalStockFirst`，见 `11-迭代1.5` 验收报告 §三）。

修法同前：**让 DDL 默认值等于零值**（`default:false`），应用层「默认启用」由 `DefaultRules()` 逐条显式写 `Enabled: true`。并加了一条纠正分支：出厂声明关闭的规则，若老库里是启用的，播种时纠正回来。

```
通过 34 项，失败 0 项

关键几条：

```
PASS 验证码一次性（不可重放）
PASS Setup 后仍为未启用（避免扫码失败锁死自己）
PASS 密码正确 + 已开2FA → 返回 need_totp 且不给 token  -- need_totp=true hasToken=false
PASS 临时票据不能访问后台接口  -- status=401
PASS 票据 + 错误动态码 → 拒  -- status=401
PASS 票据 + 正确动态码 → 拿到真令牌  -- status=200
PASS 临时票据一次性（不可重放）  -- status=401
PASS 恢复码一次性（不可重复用）  -- status=401
PASS 改动立刻生效（无需重启）  -- enabled=false priority=11
PASS 命中黑名单的注册被拒  -- status=403
PASS 风控命中已记录（可复盘）  -- count=3

## 八、遗留事项

1. **风控命中未接通知告警**（见 §五 偏差 4）。等实际命中量出来再定聚合策略，避免第一周就把告警关掉。
2. **S1–S6 六项顺手加固未做**：后台权限细化（角色-菜单表）、敏感操作二次确认、新 IP 登录告警、审计日志 before/after、导出限流、`ENCRYPTION_KEY` 轮换文档。其中 **S6 建议优先补** —— 现在换了 `ENCRYPTION_KEY` 会导致所有上游凭证、**以及所有用户的 TOTP 密钥**解不开（TOTP secret 也用它加密）。
3. **`self_purchase` 规则是空实现**：等迭代 3 的阶梯专价落地、有了上下级关系后再补判断逻辑。
4. **TOTP 密钥依赖 `ENCRYPTION_KEY`**：这条和 S6 是同一件事。密钥轮换时必须先把 `users.totp_secret` 解密-再加密，否则所有人 2FA 失效。已写进上面的 S6 待办。
5. **共享 IP 场景需调阈值**：R1（同 IP 注册 3 个/小时）在网吧/公司出口/校园网会误伤，运营应放宽或关闭。
