# 05 · UI 改造方案

> 前提：**不换技术栈。** kamihub 是 React 18 + antd 5，共 11,026 行；
> 独角数卡是 Vue 3 + Tailwind + shadcn-vue，组件一行不能拷。
>
> 本篇只讲「用 antd 做出更好的产品」这件事。

---

## 一、现状诊断（实测）

| 项 | kamihub 现状 | 问题 |
| --- | --- | --- |
| 组件库 | antd 5 | ✅ 选型正确，生态成熟 |
| 菜单 | 12 项**平铺** | 层级缺失，找不到功能 |
| 图表 | **未装任何图表库** | Dashboard 只有数字 + `Progress`，看不出趋势 |
| 主题 | 默认 antd 主题 | 视觉偏「企业中后台」，密度大、留白少 |
| 暗色 | 无（`Sider` 固定 `theme="dark"`） | 夜间运营刺眼 |
| 响应式 | 有 `Col xs/md`，但 Table 溢出 | 手机上不可用 |
| 表单 | `Goods.tsx` **43KB** 单文件 | 商品+货源+卡密全挤一个 Modal，易配错 |
| 空/错/加载态 | 部分有 | 不一致 |

### 一个具体的痛点

`Goods.tsx` 43,014 字节，是最大的单文件。它的复杂度说明一件事：
**「商品 + 挂货源 + 定价 + 卡密池」四件事被塞进了一个弹窗**。
运营配一个商品要来回切换，且极易漏填关键字段（如 `max_supply_price` 成本红线）。

这是 UI 问题，但**后果是资损**。

## 二、四件必做的事（2 天，占 80% 收益）

### U1 · 主题 token 调优（0.5 天）⭐ 性价比最高

**目标**：把「antd 默认企业中后台」调到「现代产品」质感，**不引入任何新依赖**。

```tsx
// src/theme.ts
import type { ThemeConfig } from 'antd';

export const lightTheme: ThemeConfig = {
  token: {
    // —— 圆角：默认 6 太方正，10 更现代 ——
    borderRadius: 10,
    borderRadiusLG: 14,

    // —— 主色：换一个不那么"阿里蓝"的品牌色 ——
    colorPrimary: '#2f6bff',

    // —— 布局背景：拉开层次（默认 #f5f5f5 偏灰）——
    colorBgLayout: '#f7f8fa',

    // —— 字号：正文 14 偏大，13 更紧凑但可读 ——
    fontSize: 13,
    fontSizeLG: 15,

    // —— 控件高度：默认 32 偏矮，36 更好点 ——
    controlHeight: 36,

    // —— 阴影：默认偏重，减到很轻 ——
    boxShadow: '0 1px 3px rgba(16,24,40,0.06), 0 1px 2px rgba(16,24,40,0.04)',
    boxShadowSecondary: '0 4px 16px rgba(16,24,40,0.08)',

    // —— 字体：中文优先用系统字体栈，别用默认 ——
    fontFamily: `-apple-system, "PingFang SC", "Microsoft YaHei", "Segoe UI", sans-serif`,
  },
  components: {
    Card: { paddingLG: 20 },          // 卡片内边距默认 24，20 更紧凑
    Table: {
      headerBg: '#fafbfc',            // 表头浅灰，与内容区分
      headerColor: '#5a6478',
      cellPaddingBlock: 12,           // 默认 16，行高降一点
    },
    Menu: {
      itemBorderRadius: 8,
      itemMarginInline: 8,            // 侧边栏菜单左右留白
    },
    Button: { primaryShadow: 'none' },// 主按钮不要阴影，更干净
  },
};

// 暗色：antd 5 内置算法，一行搞定
export const darkTheme: ThemeConfig = {
  ...lightTheme,
  algorithm: theme.darkAlgorithm,
  token: { ...lightTheme.token, colorBgLayout: '#0f1115' },
};
```

**效果对比**：

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 卡片 | 直角、重阴影 | 10px 圆角、极轻阴影 |
| 表格 | 全白、表头同色 | 表头浅灰、行高更松 |
| 侧边栏 | 菜单贴边 | 左右 8px 留白、项圆角 8 |
| 整体 | 偏「后台管理系统」 | 偏「SaaS 产品」 |

**这一项不需要改任何业务代码，只加一个 `<ConfigProvider theme={...}>` 包裹。**

### U2 · 菜单信息架构重组（0.5 天）

**现状**：12 项平铺

```
概览 · 订单 · 提货链接 · 上游商品 · 商品与货源 · 平台管理
日志 · C端商城 · 在线支付 · 用户 · 访问令牌 · 使用准则 · 系统设置
```

**问题**：`上游商品`/`商品与货源`/`平台管理` 是一组，但被 `提货链接` 隔开；
`C端商城`/`在线支付` 属于运营，却夹在系统项之间。

**改造后**（4 组 + 1 个散项）：

```
📊 概览
─────────────
🛒 交易
   ├─ 订单
   ├─ 提货链接
   └─ 在线支付
─────────────
📦 货源
   ├─ 上游商品
   ├─ 商品与货源
   └─ 平台管理
─────────────
👥 运营
   ├─ C 端商城
   ├─ 买家管理          ← 新增（现在藏在 C端商城 Tab 里）
   ├─ 分销管理          ← 新增（分销上线后）
   └─ 营销（券/等级）    ← 新增（P2）
─────────────
⚙️ 系统
   ├─ 日志
   ├─ 用户
   ├─ 访问令牌
   ├─ 使用准则
   └─ 系统设置
```

**antd 实现**：`Menu` 的 `items` 支持 `children`，改成 `type: 'group'` 分组即可，
路由不用动。

### U3 · 图表看板（1 天）⭐ 收益最高

**装什么**：`recharts`

| 候选 | 结论 |
| --- | --- |
| `echarts` | 功能最强但包大（~1MB），API 命令式，与 React 略别扭 |
| **`recharts`** | ✅ React 原生组件式，~120KB，与 antd 风格协调 |
| `antv/g2` | 阿里系，中文文档好，但生态偏重 |

```bash
npm i recharts
```

**看板要放的 6 个图**（对应真实运营决策）：

| # | 图 | 类型 | 回答什么问题 |
| --- | --- | --- | --- |
| C1 | 近 7/30 天订单量与毛利 | 双轴折线 | 生意在涨还是跌 |
| C2 | 订单状态分布 | 环形图 | 失败率是否异常 |
| C3 | **货源成本对比** | 横向条形 | 哪家最便宜，该切哪家 |
| C4 | **各上游成功率** | 折线 | 哪个上游在恶化 |
| C5 | 每日消耗 vs 余额 | 面积图（含预测线） | **还有几天要充值** |
| C6 | 商品销量 TOP 10 | 条形 | 该重点补哪个货 |

> **C5 是最值钱的一个图。** 它把「余额告警」变成「看得见的趋势」，
> 你能提前 3 天知道要充值，而不是等到卖不出去。

**DataViz 原则（避免做成花架子）**：
- 一个图只回答一个问题，不要塞双 Y 轴三指标
- 颜色克制：主色 + 灰阶，红色只用于「异常」
- 数字比图重要：关键指标用大字号 `Statistic`，图做趋势
- 空数据要有 `Empty`，不要让图表崩

### U4 · 商品配置向导（2 天，P2 但强烈建议提前）

**现状**：`Goods.tsx` 43KB，一个 Modal 里塞了商品信息 + 货源列表 + 卡密池 + 定价。

**改造**：拆成 `Steps` 向导（新建时），编辑时用 Tabs。

```
新建商品
┌──────────────────────────────────────────────┐
│ ① 基础信息 → ② 挂货源 → ③ 定价 → ④ 卡密(可选) │
└──────────────────────────────────────────────┘

Step 1  基础信息
  商品编码*（唯一）、名称*、分类、图片、描述
  发货方式（卡密/内容/人工）
  ┌─ 高级 ──────────────────────────┐
  │ 路由策略 / 故障转移 / 最大尝试次数  │
  └────────────────────────────────┘

Step 2  挂货源  ★ 核心步骤
  [ + 添加上游商品 ]
  ┌────────┬──────┬──────┬──────┬──────┐
  │ 平台    │ 商品号│ 成本 │ 库存 │ 优先级│
  ├────────┼──────┼──────┼──────┼──────┤
  │ 16688  │ SG…  │ ¥165 │ 120  │ 10   │
  │ 16688  │ SG…  │ ¥150 │ 8    │ 20   │
  └────────┴──────┴──────┴──────┴──────┘
  ✅ 保存时会向上游校验（GetGoods + Quote），失败当场报错

Step 3  定价
  售价*（必填，> 0 才能上架）
  ⚠️ 成本红线 MaxSupplyPrice  ← 强烈建议填写
     实时提示：当前最低成本 ¥150，建议红线 ≤ ¥165
  毛利测算：售价 178 − 成本 150 = ¥28（15.7%）

Step 4  卡密池（仅本地发货商品）
```

**为什么值得做**：这不是「好看」，是把「配置项」变成「有校验、有提示的流程」。
`MaxSupplyPrice` 漏填会导致亏本采购 —— 向导里用实时成本引导填写，能直接防住。

## 三、次要项（P2，各 0.5–1 天）

### U5 · 暗色模式

antd 5 原生支持，加一个 `ConfigProvider` 切换 + localStorage 记住选择 + 跟随系统。

```tsx
const [dark, setDark] = useState(
  () => localStorage.theme === 'dark'
     || (!localStorage.theme && matchMedia('(prefers-color-scheme: dark)').matches)
);
<ConfigProvider theme={dark ? darkTheme : lightTheme}>
```

注意：`styles.css` 里硬编码的颜色（`#fff` 等）要改成 CSS 变量，否则暗色下会糊。
这是唯一的工作量所在。

### U6 · 移动端适配

| 问题 | 修法 |
| --- | --- |
| Table 溢出 | `scroll={{ x: 'max-content' }}` |
| 详情 Drawer 太窄 | `width={isMobile ? '100%' : 720}` |
| 工具栏按钮挤 | 收进「更多」下拉 |
| 侧边栏 | 已有 `breakpoint="lg"`，ok |
| 表单两列 | `Col xs={24} md={12}` |

用 `Grid.useBreakpoint()` 统一判断，不要到处写 `window.innerWidth`。

### U7 · 状态可视化

订单详情加 `Timeline`（`Orders.tsx` 已有 Timeline 依赖）：

```
● 下单         10:23:01   （0ms）
● 选源         10:23:01   命中策略 priority
● 上游下单     10:23:02   16688 / SG20001  （820ms）
● 等待发货     10:23:02   轮询中
● 发货完成     10:23:35   卡密 1 张  （33s）
```

数据来自现有 `OrderAttempt` 表，**不需要新表**。

### U8 · 空/错/加载态统一

| 状态 | 统一组件 |
| --- | --- |
| 加载 | `Skeleton`（列表）/ `Spin`（表单提交） |
| 空 | 统一 `Empty` + **引导文案 + 行动按钮**（"还没有商品，[去添加]"） |
| 错 | `ErrorBoundary` 已有，补「重试」按钮 |
| 无权限 | 统一 403 页 |

## 四、明确不做（避免浪费）

| 项 | 为什么不做 |
| --- | --- |
| 引入 Tailwind | 与 antd 样式打架、包体积翻倍、学习成本 |
| 引入 shadcn | 是 Vue 生态，React 版不成熟；且需 Tailwind |
| 换 Vue 重写 | 11,026 行，收益为负 |
| 做深色主题的完整设计系统 | 单店内部系统，不需要 |
| 复杂动效/过渡 | 后台系统动效是干扰 |
| 自定义图标库 | `@ant-design/icons` 够用 |

## 七、一个提醒

UI 改造最容易失控的地方是「顺手把整个后台重做一遍」。

**纪律**：
1. 每次只改一个页面，改完立刻验收
2. 不改业务逻辑，只改呈现（除 U4 向导需要拆分表单）
3. 保留 `git` 提交粒度小，出问题好回滚

> 请先完成 `git init`（见 `06-实施计划.md` P0-1），否则 UI 改造回滚会很痛苦。
