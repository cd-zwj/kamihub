> 目标：把独角数卡（Dujiao-Next）中经过验证的工程优点，**有选择地**引入 kamihub，

> 本文档集是「设计文档 + 实施计划」，不含代码实现。代码在计划评审通过后分阶段落地。

## 一、三条硬约束（先读这一节）

这三条决定了后面「什么该做、什么不该做」。跳过这节直接看功能清单，很容易做出过度工程。

### 约束 1：定位是「单店自营」，不是 SaaS

kamihub 是**自建卡网**，单租户、自营、自己就是老板。
这个定位决定了独角数卡一大批能力**不该引入**：

| 独角数卡能力 | 结论 | 理由 |
| --- | --- | --- |
| 多租户 / Casbin 细粒度 RBAC | ❌ 不做 | 单店只有 `admin` / `operator` 两个角色，加一张「角色-菜单」表足够 |
| 上游批发协议 `upstreamapi` | 🟡 暂缓 | 只有要「给别的站长供货」时才需要，见 §4 |
| 广告代理 `adproxy` | ❌ 不做 | 与业务无关 |
| 购物车 `cart` | ❌ 不做 | 代充客单价低、决策快，购物车反而增加摩擦 |
| 完整合规模块 `compliance` | 🟡 只取要点 | 保留实名提示、风险告知、日志留存；不搬整套流程 |

> **判断标准**：一个功能如果是「服务多个商家」才需要的，kamihub 就不要。
> 如果是「让一家店运营得更稳/更赚钱」的，才考虑。

### 约束 2：授权 GPL-3.0，只学思想不抄代码

独角数卡是 **GPL-3.0**，kamihub 是自研闭源项目。

- ✅ **可以**：读它的架构、模块划分、状态机设计、问题分解方式，然后用**自己的代码**实现
- ❌ **不可以**：把它的 `.go` / `.vue` 文件复制进来改改变量名
- **理由**：GPL-3.0 具传染性，一旦构成衍生作品，kamihub 必须整体以 GPL-3.0 开源。
  对一个商业代充站来说，这等于把代码资产送给竞争对手。

> 本文档描述的所有设计均为「**思路借鉴 + 独立实现**」，
> 不包含任何独角数卡源码片段。落地时也请守住这条线。

### 约束 3：技术栈后端可深借，前端只借范式

| | kamihub | 独角数卡 | 可复用度 |
| --- | --- | --- | --- |
| 后端 | Go 1.25 + Gin + GORM + PostgreSQL | Go 1.26 + Gin + GORM | ⭐⭐⭐⭐⭐ 可按同样思路独立重写 |
| 前端 | React 18 + antd 5 | Vue 3 + Tailwind v4 + shadcn-vue | ⭐⭐ 只能借信息架构与视觉密度，**组件一行不能拷** |

**明确否掉的一个方案：不要为了「像独角数卡」把 React 换成 Vue。**
kamihub 有 11,026 行前端，重写收益为负；antd 5 的 token 系统足以调出接近的质感。

## 二、核心结论（TL;DR）

### 2.1 最该做的一件事

**补运维地基。** kamihub 现在 `main.go` 里**一个定时任务都没有**，导致：

| 现状 | 后果 |
| --- | --- |
| 库存不自动同步（`SyncSupplyStock` 只有后台按钮） | **超卖**，买家付钱后没货 |
| 超时支付单不自动关（`ExpireStale()` 定义了但无人调用） | 订单号/库存被占用 |
| 卡单不自动补偿（`RetryQuery` 只有人工点） | 买家等不到货，客服压力 |
| 无对账 | 上游成功、本地失败 → **钱花了货没发** |
| 无告警 | 上游挂了、余额没了、封号了，全都不知道 |

这不是「功能缺失」，是**运营风险**。优先级高于任何新功能。

### 2.2 最该做的一个新功能

**销售阶梯专价**（卖得越多、拿货价越低）。理由：代充是月付型刚需、复购高，
让销售帮你卖比自己投流便宜一个数量级。

⚠️ **不做返佣分销，改做阶梯专价**（详见 `03-销售阶梯专价设计.md`）：

> **① 返佣在你这里行不通。**
> 成本 110 / 售价 120，毛利率 8.33%。扣完 0.25% 手续费后剩 ¥9.70，
> 再留 4% 净利，**最多只能给佣金 ¥4.90/单** —— 销售卖 100 单才赚 ¥490，没人会为这个干活。
>
> **② 阶梯专价让销售赚「他自己的加价」，不消耗你的毛利。**
> 专价 114，销售卖 130 → 他赚 16；你稳赚 4。吸引力高 3 倍以上。
>
> **③ 你的支付费率是 0.25%，这是最大的成本优势。**
>
> | 费率 | 零售净利率 | 最大让价 | 可分档数 |
> | --- | --- | --- | --- |
> | **0.25%（你的）** | **8.08%** | **7 元（120→113）** | **5 档** |
> | 0.6%（官方） | 7.73% | 7 元 | 5 档 |
> | 3.5%（易支付） | 4.83% | 3 元（120→117） | 2 档 |
>
> 0.25% 完全支持 5 档阶梯，方案直接可用。
> ⚠️ 但 0.25% 低于行业标准，上线前须验证：**是否持牌机构（非二清）、是否含隐藏费用、结算周期、限额**。

### 2.3 明确「不做」清单（防止过度工程）

| 项 | 为什么不做 |
| --- | --- |
| 返佣分销（affiliate） | 8.33% 毛利下给不出有吸引力的佣金 |
| asynq 任务队列 | 当前 376 单量级，`time.Ticker` + DB 状态机足够；多实例时再换 |
| Casbin RBAC | 单店两角色，加张菜单表即可 |
| 购物车 | 增加下单摩擦 |
| 多租户改造 | 定位不符 |
| 前端换框架 | 11,026 行重写收益为负 |
| 照搬 35 个模块 | 实际只需要其中约 10 个 |

## 四、关于 `upstreamapi`：一个被降级的机会

上一轮讨论中，我建议「实现 `upstreamapi` 服务端协议，让 kamihub 变成别人的上游」。
在确认你是**自建卡网单店自营**之后，这条建议**降级为 P3**：

- **需要它的场景**：你把 16688 的货源，批发给其他站长（B 端供货）
- **不需要它的场景**：你只卖给自己商城的 C 端买家（当前定位）

但需要知道它存在：**这套协议是独角数卡官方标准**，实现服务端后，
kamihub 就能被任何独角数卡站点挂成上游，等于把你的货源卖给整个生态。
如果将来想做 B 端，这是现成的通道，不需要自己发明协议。

## 六、本轮的三个关键判断（供复核）

1. **运维优先于功能。** 一个新功能最多让你多赚钱；一次超卖或一次资损会让你赔钱且掉口碑。
2. **分销必须挂毛利，且比例要分档。** 毛利率 10%–20% 的结构下，
   固定比例分佣是自杀式定价；分档 + 动态上限才活得下去。
3. **UI 只做四件事。** 主题 token、菜单分组、图表看板、配置向导。
   这四件占 UI 收益的 80%，工作量 2 天。其余（暗色、移动端、动效）都是锦上添花。
