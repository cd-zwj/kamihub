## 二、S2：敏感操作二次确认

### 2.1 保护哪些操作

只保护**不可逆**的那几个，不是所有写接口：

| 接口 | 为什么算敏感 |
| --- | --- |
| `POST /api/platforms` | 写入上游 API 凭证，可把采购导向攻击者的账号 |
| `PUT /api/platforms/:id` | 同上，可改掉已有凭证 |
| `POST /api/buyers/:id/balance` | 直接改买家钱包余额，等于动钱 |
| `GET /api/goods/:id/cards?reveal=1` | 返回卡密**明文**，看了就能直接拿去卖 |

**故意不保护的**：订单查询、商品编辑、提货链接操作。
理由：这些要么可回滚，要么本身就被审计日志记着；全都要求输密码，运维会把密码写在便签上。

### 2.2 为什么用「票据」而不是每次带密码

如果每次翻页看卡密都重新输密码，实际使用中会退化成一件事：**把密码记在便签上**。

所以做成：

```
POST /api/auth/confirm {password}
  → {ticket, expires_in_seconds: 600}

后续敏感请求带 X-Confirm-Ticket: <ticket>
```

10 分钟窗口内不用重复确认。票据特性：

- **绑定 `user_id`** —— 换账号不能用别人的票
- **存在 Redis，不落库** —— 进程重启即失效，宁可多问一次
- **不消费**（可在窗口内重复使用），但退出登录时主动作废
- **关闭开关时**（`confirm_disabled`）直接放行，不用改代码发版

### 2.3 为什么用请求头而不是请求体

`GET /api/goods/:id/cards?reveal=1` 是 GET，没有请求体。
用 `X-Confirm-Ticket` 请求头让 GET / POST / PUT 走同一套逻辑，
前端只需要一个 axios 拦截器，不用在每个调用点改参数。

### 2.4 返回 428 而不是 403

`428 Precondition Required` 语义准确，且让前端能精确区分：

- `403` = 你根本没权限 → 提示「无权操作」
- `428` = 你有权限，但需要再确认一次 → 弹密码框并自动重试

### 2.5 暴力破解防护

确认接口本质上是一个「在已登录状态下校验密码」的预言机。
所以加了失败计数：**同一用户连续错 5 次锁定 10 分钟**，成功一次立刻清零。

只统计失败（`AllowN` 只读检查 → 失败才 `Fail` 记账 → 成功 `Reset`），
与登录限流同一套模式，正常用户不会被自己的正确操作拖进锁定。

### 2.6 前端

`src/components/ConfirmPasswordDialog.tsx` 全局挂一次，向 `api/client.ts` 注册。

axios 响应拦截器逻辑：

```
收到 428 + code=CONFIRM_REQUIRED
  → 清掉本地可能过期的票据缓存
  → 调 confirmPrompt()（弹出密码框）
  → 拿到新票据 → 把原请求带上新头重发
```

**只重试一次**（`config._confirmRetried`），否则用户取消或密码错时会无限循环。
用户取消时把错误正常抛给页面，由页面自己 toast。

票据缓存在内存（不存 localStorage）——关掉标签页就该失效。

## 三、S3：新 IP 登录提醒

### 3.1 数据模型

新表 `user_login_ips`（`user_id + ip` 唯一索引）：

| 列 | 用途 |
| --- | --- |
| `first_seen_at` | 告警就发生在这一刻 |
| `last_seen_at` | 最近一次登录 |
| `hit_count` | 累计次数，供排障 |
| `user_agent` | 仅用于告警文案，**不参与**「新设备」判定 |

### 3.2 为什么不用 `users.last_login_ip` 就行

因为一个人会在公司和家里来回登录。只比「上一次的 IP」的话，
他每次切换网络都会被判为「新 IP」—— 告警立刻变成噪音，然后运维关掉告警，等于没做。

存住全部历史 IP，才能做到「只有真的第一次见到的才提醒」。

**也不用 Redis 存集合**：Redis 重启或淘汰后历史全丢，会把所有 IP 重新当新的报一遍。

### 3.3 为什么只盯员工账号

买家换 IP 是常态（手机切流量、通勤换基站），对他们报警毫无意义且会淹没真正的异常。
`watchLogin()` 里显式判断 `admin` / `operator`。

### 3.4 不按 UA 判定「新设备」

浏览器升级、字体/插件变化都会改 UA，按 UA 判定会产生大量误报。
UA 只写进告警文案，让人自己判断「是不是我」。

### 3.5 一个必须修的坑：聚合窗口会吃掉 IP

notify 默认对 `level|event` 做 5 分钟聚合 —— 对运维告警是对的（否则刷爆 Telegram），
但对这条事件是**信息丢失**：合并后只剩「有新 IP 登录了后台」和一个次数，
**到底哪个 IP 反而不知道了**，而那是判断「是不是我」的唯一依据。

所以给 `notify.Message` 加了 `NoAggregate bool`，只在这一类「每条都是独立事实」的事件上置 true。

### 3.6 本次登录照常放行

这是提醒，不是拦截。新 IP 里绝大多数是本人换了网络，
拦下来只会把站长挡在自己后台外面。

### 3.7 内网地址会注明

`127.0.0.1` 告警文案会写「（本机回环地址，通常是反向代理未透传真实 IP）」——
否则站长看到会困惑。实际告警长这样：

```
账号 admin 从新 IP 127.0.0.1 登录。

时间：2026-10-21 18:18:18
IP：127.0.0.1（本机回环地址，通常是反向代理未透传真实 IP）
浏览器：node

如果是你本人（换了网络/新设备），忽略即可；
如果不是你，请立刻改密码，并检查后台是否被人改过东西。
```

## 四、配置项

都在后台「账号安全与风控 → 安全策略」里，改完**立即生效**（每次请求现读设置，不用重启）。

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `confirm_disabled` | `false` | 反向字段：零值 = **要求确认** |
| `login_alert_disabled` | `false` | 反向字段：零值 = **提醒开启** |

沿用 `captcha_disabled` / `risk_disabled` / `agent_disabled` 的约定：
设置是一行 JSON，缺失字段解码为 false。反向命名让「升级后旧配置没这个键」保持防护开启。

### 5.4 一个必须记录的教训

第一次跑冒烟时 `confirm/status` 返回了 `required:true`，但敏感接口全都放行了。
原因：`h.confirm` 根本没装配（`api.Deps` 漏了字段），而 `confirmStatus` 在
`h.confirm == nil` 时的默认值恰好也是 `required:true` —— **一个默认值把配置错误掩盖了**。

已经改掉：

- `confirmStatus` 在服务缺失时直接 500
- `requireConfirm` 在服务缺失时**失败关闭**（deny），而不是放行

放行会让「忘了装配依赖」变成一个没人发现的静默安全漏洞。

## 六、脚本兼容性改动

二次确认上线后，`e2e.mjs` 与 `smoke-hybrid.mjs` 里建平台/看卡密明文的调用会返回 428，
这是功能生效的正常表现。两个脚本改为**像真实管理员一样先换票据**，
然后所有请求带上 `X-Confirm-Ticket`。

这比在脚本里关掉功能更好：脚本走的就是真实链路，
以后谁把确认逻辑改坏了，回归会立刻失败。

## 七、仍然没有做的

按「不做会怎样」排序：

| # | 项 | 现状与判断 |
| --- | --- | --- |
| 1 | **S1 后台权限细化** | `operator` 仍能看到平台凭证。目前只有站长一个账号，暂不急；多一个员工就该做 |
| 2 | **S4 审计日志 before/after** | 只记「改了哪个字段」，不记改前改后的值。追查「他到底改成了什么」时不够 |
| 3 | **S5 导出限流** | 卡密导出目前靠 S2 的密码确认兜底，没有独立频率限制 |
| 4 | 同 IP 多账号聚类 | 需要设备指纹或 IP 画像，属独立工程量 |
| 5 | 敏感操作命中告警 | 现在确认失败写审计日志，但不推告警。若有人在试你的密码，不会主动通知 |

第 5 项是个可以考虑的补丁：它和 S3 共用同一套通知，成本很低。
但也会带来噪音（自己输错一次就报警），所以没有擅自加。

## 八、一句话总结

> S2 让「拿到你浏览器的人」不能直接改钱和数据；
> S3 让「拿到你密码的人」第一次登录就被你看见。
> 两条都只是**提高被发现和被阻止的成本**，不是绝对防护 ——
> 真正常开的那个开关是 S1（权限细分），等你加第二个后台账号时它会变成刚需。
