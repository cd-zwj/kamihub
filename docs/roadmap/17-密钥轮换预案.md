> 最后更新：2026-10

## 一、这份文档解决什么问题

kamihub 用 `ENCRYPTION_KEY`（AES-256-GCM）加密两样东西：

| 数据 | 表.列 | 解密失败的后果 |
| --- | --- | --- |
| 上游平台凭证 | `platforms.credentials` | 所有上游采购停摆，只能逐个重新录入 API key |
| 用户 TOTP 密钥 | `users.totp_secret` | **所有开了两步验证的账号永久登不进去**（只能靠一次性恢复码或人工重置） |

这两样都是**长期资产**，不是会话。所以：

- `JWT_SECRET` 换了 → 大家重新登录一次，无损失
- `ENCRYPTION_KEY` 换了 → **静默数据损失**

### 为什么是「静默」的

解密是懒加载的，服务启动时不会把所有密文解一遍。所以换错密钥之后：

```
启动          ✅ 正常
登录后台       ✅ 正常（密码是 bcrypt 哈希，与这把钥匙无关）
看订单列表     ✅ 正常
点「平台管理」  ❌ 这里才炸
```

**在你真正用到加密数据之前，一切看起来都是好的。** 这是它最危险的地方 —— 可能过了半天才发现中间进来的订单全都采购失败。

### v1.0 的处境（已解决）

早期版本的密文就是 `base64(nonce || ciphertext)`，**不携带任何「我是用哪把钥匙锁的」信息**。因此只剩两条路：要么永远不换钥匙，要么换一次就全废。本文档描述的是 v1.1 引入的完整解法。

## 二、现在的机制

### 2.1 密文自带钥匙标识

```
v1.0   base64(nonce||ciphertext)
v1.1   k<8位hex>:base64(nonce||ciphertext)
        └─ 密钥标签，由密钥自身推导（SHA-256 前 4 字节）
```

好处：

- **不需要在配置里给密钥起名字** —— 标签是算出来的，写错也不可能
- 解密时先看标签选钥匙，选不到就明确报错，不会拿错钥匙硬试
- 运维工具可以按标签统计「还有多少条没轮换」

### 2.2 密钥环（Keyring）

进程里维护一组密钥：

| 角色 | 来源 | 用途 |
| --- | --- | --- |
| 主密钥 | `ENCRYPTION_KEY` | **所有新写入都用它加密** |
| 历史密钥 | `ENCRYPTION_KEY_OLD`（可多个，逗号分隔） | **只用于解密**旧数据 |

于是换钥匙变成一个「渐进」过程，而不是「一刀切」：

```
换之前     [A]                         全站用 A
窗口期     [B 主] [A 历史]             新数据用 B，老数据靠 A 解
重新加密   [B 主] [A 历史] → rotate    全部改写成 B
收尾       [B]                         清掉 A，完成
```

### 2.3 旧格式仍然兼容

v1.0 写下的无标签密文**依然能解开**：先试主密钥，再逐个试历史密钥。GCM 带认证标签，试错只会返回失败，绝不会解出一段似是而非的明文。

所以**升级本版本不会造成任何数据不可读**，只是这些老数据会被标记为「待轮换」。

## 三、配置项

| 变量 | 必填 | 说明 |
| --- | --- | --- |
| `ENCRYPTION_KEY` | ✅ | 主密钥。`openssl rand -hex 32`，或 `keytool -mode genkey` 生成 |
| `ENCRYPTION_KEY_OLD` | ❌ | 历史密钥，**只在轮换窗口期填写**。多个用英文逗号分隔 |

校验规则（启动即检查，不通过直接退出）：

- 主密钥长度 ≥ 32
- 每个历史密钥长度 ≥ 32
- 历史密钥不能与主密钥相同（相同会提示直接删掉）

启动日志里会打印当前主密钥标签，并在处于轮换窗口时打一条 WARN：

```
level=INFO msg="加密密钥环就绪" primary_key=k9f5bb6e2 key_count=2
level=WARN msg="检测到 ENCRYPTION_KEY_OLD：当前处于密钥轮换窗口，请跑 keytool -mode rotate ..."
```

## 四、运维工具 `keytool`

位置：`backend/cmd/keytool`。在 `backend` 目录执行（能读到 `.env`），或自行注入环境变量。

```bash
# 生成一个新密钥（不碰数据库）
go run ./cmd/keytool -mode genkey

# 体检：统计每条密文用的是哪把钥匙，并尝试解密
go run ./cmd/keytool -mode status

# 只读校验：逐条解密，任何一条失败就非零退出
go run ./cmd/keytool -mode verify

# 演练：只统计会被改动多少条，不写库
go run ./cmd/keytool -mode rotate -dry-run

# 真正重新加密
go run ./cmd/keytool -mode rotate
```

参数：`-batch 500`（分批读取条数）、`-verbose`（打印 SQL）。

编译成单文件（线上推荐，不必带 Go 环境）：

```bash
cd backend
go build -o keytool ./cmd/keytool
```

### `rotate` 的并发安全

服务**可以不停机**。`rotate` 的更新语句带乐观并发控制：

```sql
UPDATE platforms SET credentials = ? WHERE id = ? AND credentials = <读到的原值>
```

受影响行数为 0 表示该行在读取后被服务改写过 —— 此时跳过并计入「并发冲突」，**绝不用读到的旧明文覆盖别人刚写的新值**。

## 五、标准轮换流程

> ⚠️ 动手前先做 **§六 备份**。没有备份就没有退路。

### 步骤 1 · 生成新密钥并备份

```bash
go run ./cmd/keytool -mode genkey
```

把新密钥抄下来。同时确认**旧密钥已在离线位置有一份备份**。

### 步骤 2 · 配置双密钥并重启

```dotenv
ENCRYPTION_KEY=新的64位hex
ENCRYPTION_KEY_OLD=旧的64位hex
```

重启服务。**此时系统完全正常**：新数据用新钥匙，老数据用旧钥匙解 —— 这是这套机制最关键的性质。

验证一下：

```bash
go run ./cmd/keytool -mode status
```

预期：`旧格式无标签` 或 `旧密钥 kXXXX` 有若干条，且**「无法解密」必须是 0**。若出现「无法解密」，**立即停止**，说明配错密钥了。

### 步骤 3 · 演练后正式重新加密

```bash
go run ./cmd/keytool -mode rotate -dry-run   # 先看会改多少条
go run ./cmd/keytool -mode rotate
```

预期输出：

```
【上游平台凭证】 扫描 46 · 重写 46 · 已是主密钥 0 · 并发冲突 0 · 失败 0
【用户 TOTP 密钥】 扫描 3 · 重写 3 · 已是主密钥 0 · 并发冲突 0 · 失败 0

✅ 轮换完成：重写 49 条，跳过 0 条（已是主密钥）。
```

若「并发冲突」不为 0：多跑一次 `rotate` 即可（幂等的）。
若「失败」不为 0：说明有数据解不开，**先查 `ENCRYPTION_KEY_OLD` 是否漏配了一把**，别继续往下走。

### 步骤 4 · 确认清零

```bash
go run ./cmd/keytool -mode status
go run ./cmd/keytool -mode verify
```

预期 `✅ 结论：没有需要轮换的记录` 且 `✅ 全部可解密`。

### 步骤 5 · 清掉旧密钥

```dotenv
ENCRYPTION_KEY=新的64位hex
# ENCRYPTION_KEY_OLD 整行删除
```

重启服务。再跑一次 `verify` 确认。

### 步骤 6 · 归档，不要立刻销毁

旧密钥**先归档保留至少 30 天**（放进密码管理器或离线介质）。理由：万一备份恢复、或某张表漏掉了，还有救。确认一切正常后再销毁。

## 六、备份要求（比轮换更重要）

> 密钥丢失 + 无备份 = 数据永久报废。这不是演练能救的。

必须满足三条：

1. **离线副本** —— 至少一份不在这台服务器上（密码管理器 / U 盘 / 纸质信封）
2. **与数据分离** —— 密钥备份不要和数据库备份放在同一个地方
3. **能验证** —— 备份里存的是完整 64 位串，不是"大概记得"

建议做法：把 `ENCRYPTION_KEY` 连同 `.env` 一起，在**首次部署当天**存入密码管理器，并写下「此密钥用于 kamihub 上游凭证与 TOTP 加密，丢失不可恢复」。

`.env` 本身**不入库**（已在 `.gitignore`）。若曾误提交过，必须立刻按本文档轮换。

## 七、常见故障

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `密文由未知密钥 kXXXX 加密，请检查 ENCRYPTION_KEY_OLD` | 少配了一把历史密钥 | 把对应旧密钥补进 `ENCRYPTION_KEY_OLD` |
| `密文为无标签的旧格式，且没有密钥能解开` | 当前所有钥匙都对不上 | 检查 `ENCRYPTION_KEY` 是否被改成别处的值；翻备份 |
| `status` 显示「无法解密 N 条」 | 同上，或数据是别的实例写入的 | **先别 rotate**，先修配置 |
| 启动报 `ENCRYPTION_KEY_OLD 第 N 项与 ENCRYPTION_KEY 相同` | 新旧配成了同一个 | 删掉那一项 |
| 后台所有平台都报"解密失败" | 服务仍是旧进程，未读到新配置 | 重启 |
| `rotate` 反复出现并发冲突 | 服务在持续写入该批记录 | 属正常，多跑几次即可 |

## 九、这次没有做的事

1. **自动轮换** —— 密钥轮换应是人工的、可审计的动作，自动轮换一旦出错就是全站数据报废。不做。
2. **密钥托管于 KMS/Vault** —— 当前规模用 `.env` + 离线备份足够。若将来多实例部署且要求密钥不落盘，再考虑接 Vault。
3. **`keytool` 的远端模式** —— 现在必须在能连到数据库的机器上跑。够用。

---

## 十、一句话总结

> 换 `ENCRYPTION_KEY` 现在是一个**可逆、可验证、可中途回滚**的三步操作：
> 配双密钥 → `rotate` → 清旧密钥。
> 但**先备份**，永远比先轮换重要。
