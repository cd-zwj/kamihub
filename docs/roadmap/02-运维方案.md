# 02 · 运维方案

> 目标：让 kamihub 从「出问题靠人工发现、人工点按钮」变成「自动同步、自动补偿、自动告警」。
>
> 本篇是 P0 的技术方案，改造原则：**纯新增，不动现有交易链路**。

---

## 一、为什么运维优先

kamihub 的核心交易链路（采购/路由/发货）已经生产验证过 376 单。真正的问题是**它不会自己运转**：

```
现实中的一天：
上午  某个货源断货了      → 买家下单失败 → 客服才知道
中午  16688 运营钱包见底  → 所有订单失败  → 全店停摆
下午  一笔订单卡在 purchasing → 没人管 → 买家投诉
晚上  易支付超时单堆积    → 库存被占    → 少卖
半夜  上游跑路            → 无人知晓
```

这些都不需要「新功能」，只需要**一个能定时干活的进程**。

---

## 二、O1：worker 双模式（0.5 天）

### 2.1 设计

kamihub 现在是单入口。改成三种运行模式，**同一份代码、同一个镜像**：

| 模式 | 作用 | 适用 |
| --- | --- | --- |
| `-mode all` | HTTP + 定时任务 | 本地开发、小规模单机 |
| `-mode api` | 只起 HTTP | 生产（与 worker 分离） |
| `-mode worker` | 只跑定时任务 | 生产（与 api 分离） |

**为什么值得拆**：
- 定时任务卡住/崩了，不影响买家下单（反之亦然）
- 可以单独重启、单独扩容
- 定时任务可以关掉（比如维护窗口），不用停整站

### 2.2 骨架（独立实现）

```go
// cmd/server/main.go
var mode = flag.String("mode", "all", "运行模式: all|api|worker")

func main() {
    cfg := config.Load()
    deps := bootstrap(cfg)          // 装配依赖（现有逻辑抽出）

    var g errgroup.Group
    if *mode == "all" || *mode == "api" {
        g.Go(func() error { return runHTTP(deps, cfg) })
    }
    if *mode == "all" || *mode == "worker" {
        g.Go(func() error { return worker.Run(deps) })
    }
    // 统一监听 SIGINT/SIGTERM，ctx 取消后两个 goroutine 一起优雅退出
    ...
}
```

### 2.3 部署变更

`docker-compose.yml` 从 4 个服务变成 5 个（backend 拆两个）：

```yaml
backend-api:
  image: kamihub-backend:1.0.0
  command: ["-mode", "api"]
  ...
backend-worker:
  image: kamihub-backend:1.0.0   # 同一个镜像
  command: ["-mode", "worker"]
  ...
```

> 如果暂时不想改 compose，可以先用 `-mode all` 单容器跑，**代码不用改**。

## 三、O2：定时任务中心（2 天）

### 3.1 技术选型决策

| 方案 | 结论 |
| --- | --- |
| asynq（Redis 队列） | ❌ 当前不引入 |
| `time.Ticker` + `errgroup` + DB 状态机 | ✅ **采用** |

**理由**：
- 当前量级（376 单累计、单实例）用不到 asynq 的分布式抢任务、持久化重试
- `time.Ticker` 零新依赖、零运维成本、调试直观
- **关键前提**：所有任务必须写成**幂等**的。这样将来换 asynq 只是换调度器，任务函数不用改

**升级信号**：当出现「多副本部署」或「任务绝对不能丢」需求时，再换 asynq。

### 3.2 五个任务

目录：`internal/worker/`（新增包）

```go
// internal/worker/worker.go
type Task struct {
    Name     string
    Interval time.Duration
    Timeout  time.Duration
    Run      func(ctx context.Context) (Result, error)
}

func Run(deps *Deps) error {
    tasks := []Task{
        stockSyncTask(deps),      // 库存同步
        balanceSyncTask(deps),    // 余额同步
        expirePaymentTask(deps),  // 超时支付单关闭
        staleOrderTask(deps),     // 卡单补偿
        reconcileTask(deps),      // 对账
    }
    // 每个任务独立 goroutine + ticker
    // 单次执行加超时；panic 用 recover 兜住，绝不让一个任务拖死整个 worker
}
```

#### 任务 1：库存同步 `stock_sync`

| 项 | 值 |
| --- | --- |
| 频率 | 热销货源 2 分钟 / 长尾 30 分钟（按 `Supply` 最近 24h 出单量分级） |
| 逻辑 | 遍历 `enabled=true` 的 `Supply` → 调 `Client.GetGoods(goodsNo)` → 更新 `Stock` / `StockSyncedAt` / `LastCheckOK` / `LastCheckMsg` |
| 幂等 | ✅ 纯覆盖写，天然幂等 |
| 限流 | 按 `Platform.RateLimitPerMin` 控制并发，避免打爆上游 |
| 失败处理 | 单条失败不影响其他；连续失败 N 次标记 `LastCheckOK=false` 并触发通知 |

> **热销分级**：查最近 24h `order_attempts` 中该 `supply_id` 的出现次数，>5 次算热销。
> 避免对长尾商品高频轮询浪费上游配额。

#### 任务 2：余额同步 `balance_sync`

| 项 | 值 |
| --- | --- |
| 频率 | 5 分钟 |
| 逻辑 | 遍历 `enabled=true` 的 `Platform` → `Client.Ping()` → 更新 `Balance` / `BalanceSyncedAt` |
| 幂等 | ✅ |
| 告警 | `balance < 预警阈值`（建议 = 日均消耗 × 2）→ 通知 |

> **这是 16688 场景的命门**：采购扣的是 `operate_money`（运营钱包），
> 余额为 0 时**所有订单直接失败**。没有这个任务，你是「卖到没钱了才知道」。

#### 任务 3：超时支付单关闭 `expire_payment`

| 项 | 值 |
| --- | --- |
| 频率 | 1 分钟 |
| 逻辑 | 调现有 `PaymentService.ExpireStale()`（**已实现，只是没人调**） |
| 幂等 | ✅ 已实现为状态机流转 |

> 这是**零成本收益**：代码已经写好，接上定时器就能用。

#### 任务 4：卡单补偿 `stale_order`

| 项 | 值 |
| --- | --- |
| 频率 | 2 分钟 |
| 逻辑 | 扫 `status=purchasing AND updated_at < now-5min AND platform_trade_no != ''` → 调 `OrderService.RetryQuery()` 重新查上游 |
| 幂等 | ✅ 查单天然幂等 |
| 边界 | **不重下新单**，只查已下单的；避免重复扣款（这是 kamihub 已有的铁律） |
| 兜底 | 超过 30 分钟仍未决 → 标记需人工 + 通知 |

> 注意区分两类：
> - 有 `platform_trade_no` → 上游单已建，**只查单，绝不换源**
> - 无 `platform_trade_no` → 上游单没建成，可安全重试（由人工或后续规则决定）

#### 任务 5：对账 `reconcile`

见 §四。

### 3.3 任务运行记录

新增表 `worker_task_runs`，记录每次执行（便于排查「任务到底跑没跑」）：

```sql
CREATE TABLE worker_task_runs (
  id           bigserial PRIMARY KEY,
  task         varchar(64)  NOT NULL,   -- stock_sync / balance_sync / ...
  started_at   timestamptz  NOT NULL,
  finished_at  timestamptz,
  ok           boolean      NOT NULL DEFAULT false,
  affected     bigint       NOT NULL DEFAULT 0,
  error_msg    text,
  duration_ms  bigint       NOT NULL DEFAULT 0
);
CREATE INDEX idx_wtr_task_started ON worker_task_runs (task, started_at DESC);
```

后台「日志」页加一个 Tab 展示，运维一眼能看出哪个任务挂了。

## 四、O3：对账模块（2 天）

### 4.1 为什么必须做

对账解决的是**这一类资损**：

```
场景 A：向 16688 下单成功，但 HTTP 响应超时
  → 本地记 failed，钱扣了，货在上游
  → 买家投诉没收到，你退款，上游的钱白付

场景 B：上游发货了，但本地写库失败
  → 本地 pending 永远不动，买家以为没发货

场景 C：易支付回调丢了
  → 买家付了钱，余额没到账
```

这三个都是**低频但必然发生**的，且都是真金白银。

### 4.2 设计

新增 `internal/service/reconcile.go` + 表：

```sql
CREATE TABLE reconcile_diffs (
  id            bigserial PRIMARY KEY,
  biz_date      date         NOT NULL,   -- 归属日期（按 Asia/Shanghai）
  kind          varchar(32)  NOT NULL,   -- order_missing_local / order_status_mismatch /
                                          -- wallet_frozen_stale / payment_not_settled
  order_no      varchar(64),
  platform_id   bigint,
  trade_no      varchar(128),
  local_status  varchar(32),
  remote_status varchar(32),
  amount        numeric(12,2),
  detail        jsonb,
  resolved      boolean      NOT NULL DEFAULT false,
  resolved_by   bigint,
  resolved_at   timestamptz,
  created_at    timestamptz  NOT NULL DEFAULT now()
);
CREATE INDEX idx_rd_open ON reconcile_diffs (resolved, biz_date DESC);
```

### 4.3 对账的四个维度

| 维度 | 比对对象 | 检查内容 | 处理 |
| --- | --- | --- | --- |
| **订单** | 本地 `orders` ↔ 上游 `purchase/list` | 上游有、本地无 → 补单；状态不一致 → 以**上游为准**修正本地 | 自动修复 + 记录 |
| **钱包** | `wallet_transactions` ↔ `buyers.balance` | 累计流水 ≠ 余额快照 | **只告警不自动改**（钱的事必须人工确认） |
| **冻结** | `wallet_transactions(status=frozen)` | 超过 30 分钟未结算/未退款 | 自动解冻退款 |
| **支付** | `payment_orders` ↔ `wallet_transactions` | 已 paid 但无对应入账流水 | 自动补入账 + 告警 |

### 4.4 执行策略

- **频率**：每小时一次（全量），每日 03:00 做一次「昨日」完整对账
- **上游窗口**：16688 无增量接口，只能 `purchase/list` 分页全量拉取 → 按时间窗过滤
- **只读优先**：第一版**只检测、只记录、不自动改库**。运营在后台确认后手动点修复。
  跑稳两周后再开自动修复。**这是保守但正确的顺序。**

## 五、O4：单二进制 embed 前端（0.5 天）

### 5.1 现状

```
backend 容器（:18080） + web 容器（Nginx :8090 托管 dist） + 外层 Nginx（TLS）
```
三层转发，部署要同步两个镜像。

### 5.2 方案

kamihub 已经对模板用了 `go:embed`（`render/render.go`），扩展一下即可：

```go
// internal/webui/embed.go
package webui

import (
    "embed"
    "io/fs"
)

//go:embed all:dist
var assets embed.FS

func FS() fs.FS {
    sub, _ := fs.Sub(assets, "dist")
    return sub
}
```

构建流程（Dockerfile 多阶段）：
```
Stage 1: node  → npm run build        → 产出 dist
Stage 2: golang → 拷入 dist + go build → 单二进制（含前端）
Stage 3: alpine → 只放二进制
```

路由接法：在 Gin 里注册 `NoRoute` 兜底到 SPA：

```go
r.NoRoute(func(c *gin.Context) {
    p := c.Request.URL.Path
    if strings.HasPrefix(p, "/api") || strings.HasPrefix(p, "/d/") {
        c.Status(404); return
    }
    // 尝试静态文件，找不到回退 index.html（SPA 路由）
})
```

### 5.3 收益与风险

| 收益 | 风险 |
| --- | --- |
| 部署从「两镜像 + 两层反代」变成「一个文件 + systemctl」 | 前端更新要重新编译后端（~1 分钟） |
| 少一个容器、少一个 Nginx 配置 | 二进制体积 +1.5MB |
| 前后端版本天然一致（不会出现「前端新后端旧」） | 无法单独灰度前端 |

> **注意**：仍需保留外层 Nginx 做 TLS 终止。embed 只是省掉**内层** web 容器。
> 属 P1，不是 P0 —— 它不解决问题，只简化部署。

## 六、O5：架构守护测试（0.5 天）

### 6.1 这是独角数卡最被低估的优点

它有一类测试专门断言「**模块之间不许乱依赖**」。这不是功能测试，是**防腐测试**。

kamihub 目前靠自觉维持分层。随着代码从 15,791 行往上长，迟早会出现
`service` 反调 `api`、`platform` 依赖 `service` 这类循环。

### 6.2 实现（零依赖，用标准库 `go/parser`）

```go
// internal/archtest/arch_test.go
package archtest

// 规则表：包 → 禁止 import 的前缀
var rules = map[string][]string{
    "kamihub/internal/platform":  {"kamihub/internal/service", "kamihub/internal/api"},
    "kamihub/internal/routing":   {"kamihub/internal/service", "kamihub/internal/api", "kamihub/internal/platform"},
    "kamihub/internal/service":   {"kamihub/internal/api"},
    "kamihub/internal/models":    {"kamihub/internal/service", "kamihub/internal/api", "kamihub/internal/platform"},
}

func TestLayering(t *testing.T) {
    // 遍历 internal/**/*.go，解析 import，断言不违反 rules
}
```

### 6.3 建议的规则集

| 包 | 禁止依赖 | 理由 |
| --- | --- | --- |
| `models` | 任何上层 | 模型层必须是最底层的纯数据结构 |
| `platform` | `service` / `api` | 适配器不该知道业务 |
| `routing` | `service` / `api` / `platform` | 路由策略是纯函数 |
| `service` | `api` | 业务层不该知道 HTTP |

## 七、验收标准

### worker 验收

- [ ] `-mode api` 启动后**没有**任何定时任务在跑（日志确认）
- [ ] `-mode worker` 启动后**不监听**任何端口
- [ ] 五个任务在 `worker_task_runs` 都有记录
- [ ] 手动把某 `Supply.stock` 改成 0，等 2 分钟后被真实值覆盖
- [ ] 手动造一条 `status=purchasing` + `updated_at` 为 1 小时前的订单，2 分钟内被查到
- [ ] 手动造一条 `payment_orders(status=pending, expires_at=过去)`，1 分钟内变 expired
- [ ] 停掉 Redis，worker 不崩（降级继续）

### 对账验收

- [ ] 在测试环境手工造 4 类差异，全部能被 `reconcile_diffs` 捕获
- [ ] 修复动作可重复执行（幂等）
- [ ] 对账任务本身不产生任何写操作（第一版）

### 通用

- [ ] `go test ./...` 全绿
- [ ] 新增代码有单测，任务函数覆盖「幂等」「超时」「上游报错」三态
- [ ] 现有 41 项 e2e 全部仍通过（**回归红线**）

## 八、风险与回滚

| 风险 | 应对 |
| --- | --- |
| 定时任务打爆上游限流 | 严格按 `RateLimitPerMin` 控制并发；首版把频率调保守（库存 5min 起） |
| 对账自动改库改错 | **第一版只检测不改库**；自动修复需人工开启 |
| worker 与 api 抢锁 | 任务用 PG advisory lock 保证同一时刻只有一个实例在跑 |
| 部署改坏 | 保留 `-mode all` 单容器模式作为回滚路径，改回 compose 即可 |

**回滚方案**：worker 是纯新增包，`git revert` 后 `-mode` 参数忽略即可，不影响任何现有代码路径。
