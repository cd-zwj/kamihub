# 03 · 销售阶梯专价系统设计（专项）

> 本篇替代原「返佣分销」方案。
>
> **最终结论：不做返佣分销，改做「按销量拿专价」的阶梯批发价体系。**
> 因为毛利率只有 8.33%，返佣给不出有吸引力的钱；而阶梯专价能让销售自己赚差价，
> 你的毛利按档位锁定，不被动分成。

---

## 一、为什么放弃返佣，改阶梯专价

### 1.1 返佣方案在你这里行不通

成本 ¥110 / 售价 ¥120，毛利率 **8.33%**。

| 项 | 数值 |
| --- | --- |
| 毛利 | ¥10 |
| 支付手续费（易支付 3.5%） | ¥4.20 |
| 扣费后剩余 | ¥5.80 |
| 若保留 4% 净利（¥4.80） | **可给佣金 ¥1.00** |

¥1/单的佣金，销售卖 100 单才赚 ¥100。**没有人会为这个干活。**

### 1.2 阶梯专价的逻辑完全不同

```
返佣：销售卖 120，从你的 ¥10 毛利里分走一块 → 你越卖越薄
专价：销售按 116 拿货，自己卖 130 → 赚 14；你稳赚 6（扣费前）
```

**关键区别：专价模式下，销售赚的是「他自己的加价」，不消耗你的毛利。**
你只需要在「让价」和「走量」之间找一个平衡点，而这个平衡点由销量档位自动调节。

### 1.3 两种模式对比（同一件成本 110 的商品）

| | 返佣 | 阶梯专价 |
| --- | --- | --- |
| 你定价 | 120（统一） | 120 零售 + 分档专价 |
| 销售赚什么 | 从你毛利里分 | 自己的零售加价 |
| 你能给销售最多 | ¥5.80（再给就归零） | 让价 ¥3–7（专价 117→113） |
| 销售实际能赚 | ¥1–5.8 | **¥14–27**（自己加价） |
| 你的毛利 | 越卖越薄 | **按档位锁定** |
| 结算/提现/冲正 | 全部要写 | **不需要** |
| 开发量 | 6.5 天 | **3 天** |

> **结论：阶梯专价对销售吸引力高 3–5 倍，且你的成本结构可控。**

## 二、命门：支付手续费决定阶梯能拉多开

这是本篇最重要的一节。**很多人设计阶梯定价时忘了算支付手续费，结果越卖越亏。**

### 2.1 你的费率是 0.25%，这给了很大空间

成本 110，零售 120。专价每让 1 元，你的毛利就少 1 元，但手续费按专价百分比扣，几乎不变。

| 专价 | 你毛利 | 手续费（0.25%） | 净利 | 净利率 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 120 | 10.00 | 0.300 | 9.700 | **8.08%** | 零售 |
| 119 | 9.00 | 0.298 | 8.703 | 7.31% | |
| 118 | 8.00 | 0.295 | 7.705 | 6.53% | 铜牌 |
| 117 | 7.00 | 0.293 | 6.708 | 5.73% | |
| 116 | 6.00 | 0.290 | 5.710 | 4.92% | 银牌 |
| 115 | 5.00 | 0.288 | 4.713 | 4.10% | |
| 114 | 4.00 | 0.285 | 3.715 | 3.26% | 金牌 |
| **113** | 3.00 | 0.283 | 2.718 | **2.40%** | 钻石（极限） |
| 112 | 2.00 | 0.280 | 1.720 | 1.54% | ❌ 低于保底 |
| 111 | 1.00 | 0.278 | 0.723 | 0.65% | ❌ |

**结论：0.25% 费率下，阶梯空间能到 120 → 113，可让 7 元，5 档全部可用。**

### 2.2 对比：如果你的费率是 3.5%（易支付）

同样成本 110 / 零售 120：

| 专价 | 净利（3.5%） | 净利率 | 能否用 |
| --- | --- | --- | --- |
| 120 | 5.80 | 4.83% | ✅ 零售 |
| 118 | 3.87 | 3.28% | ✅ 铜牌 |
| 117 | 2.91 | 2.48% | 🟡 极限 |
| 116 | 1.94 | 1.67% | ❌ 低于保底 |
| 114 | 0.01 | 0.01% | ❌ 归零 |
| 113 | −0.96 | −0.85% | ❌ 亏钱 |

**3.5% 费率下只能分 2 档、让 3 元。**

### 2.3 三种费率对比（这是本篇的核心结论）

| 费率 | 零售净利率 | 最大让价 | 可分档数 | 销售能赚（卖130） |
| --- | --- | --- | --- | --- |
| **0.25%（你的）** | **8.08%** | **7 元（120→113）** | **5 档** | **¥16–17** |
| 0.6%（官方） | 7.73% | 7 元（120→113） | 5 档 | ¥16–17 |
| 3.5%（易支付） | 4.83% | 3 元（120→117） | 2 档 | ¥12 |

> **你的 0.25% 比官方 0.6% 还低，比易支付 3.5% 低 14 倍。**
> 这个费率结构下，阶梯专价方案完全成立，不需要先换通道。

### 2.4 ⚠️ 但必须验证这个 0.25% 的真实性

0.25% 低于微信/支付宝官方标准费率（0.6%），这在国内通常只有几类来源。
**不同类型对应完全不同的风险，必须先确认：**

| 来源 | 典型费率 | 资金风险 | 稳定性 |
| --- | --- | --- | --- |
| 银行直连 / 银联云闪付 | 0.2%–0.38% | 🟢 低（持牌机构） | 高 |
| 数字人民币 | ≈0 | 🟢 低 | 中（覆盖有限） |
| 官方通道的优惠期/大客户价 | 0.2%–0.38% | 🟢 低 | 需看协议期限 |
| **第四方「二清」通道** | **0.2%–0.3%** | 🔴 **高** | 🔴 低 |
| 混淆了「交易费」和「提现费」 | — | 🟡 中 | — |

**必须确认的四件事：**

1. **是持牌机构还是第四方？** 二清通道有资金被冻结、跑路的风险
2. **0.25% 是否含全部费用？** 有些通道交易费低但另收提现费、结算费、拒付罚金
3. **结算周期是 T+0 / T+1 还是 T+N？** 周期越长，你的现金流压力越大
4. **有没有单笔/单日限额？** 限额低会直接卡住大单

> 这不是合规说教，是**实打实的资金风险**：
> 代充是高频、小额、投诉率高的品类，是低费率通道的重点风控对象。
> 一旦通道冻结资金，你的库存和余额都还在，但钱拿不出来。

**建议动作**：把费率写进 `PAY_FEE_RATE` 环境变量前，
先做一笔真实小额交易，核对「到账金额 = 订单金额 × (1 − 0.25%)」，
并确认没有隐藏扣费。**如果实际费率是 0.6% 或更高，保底公式会自动收紧档位，不会亏本**——
但你的阶梯会变窄，需要重新调档位表。

### 2.5 保底公式（写死在代码里）

专价不能低于成本线，且必须留出最低净利：

```
专价下限 = max(
    成本 × (1 + 最低毛利率),                      // 防亏本
    (成本 + 零售价 × 最低净利率) / (1 − 手续费率)   // 防手续费吃光
)
```

**按你的 0.25% 计算（成本 110 / 零售 120 / 最低净利率 2%）**：

```
保底① = 110 × 1.02 = 112.20
保底② = (110 + 120 × 0.02) / (1 − 0.0025)
      = 112.40 / 0.9975
      = 112.68

专价下限 = max(112.20, 112.68) = 112.68
```

**逐档验证**：

| 档位 | 专价 | ≥ 112.68？ | 结果 |
| --- | --- | --- | --- |
| 钻石 | 113.00 | ✅ | 可用 |
| 金牌 | 114.00 | ✅ | 可用 |
| 银牌 | 116.00 | ✅ | 可用 |
| 铜牌 | 118.00 | ✅ | 可用 |
| 零售 | 120.00 | ✅ | 可用 |

> **5 档全部可用。** 但注意：钻石档 113 只比保底线高 0.32 元，
> 如果某个商品成本略高（比如 111），钻石档就会自动失效并回落到金牌。
> **这就是为什么「逐级回落」必须写在代码里，不能靠人工判断。**

**任一条不满足 → 该档位对该商品不生效**（自动回落到上一档），
并在后台标红提示「该商品毛利不足以支持此档位」。

## 三、档位设计

### 3.1 推荐档位（按你的 0.25% 费率）

成本 110 / 零售 120 时：

| 档位 | 达成条件（近 30 天） | 折扣率 | 专价 | 让价 | 你净利率 |
| --- | --- | --- | --- | --- | --- |
| `retail` 零售 | 默认 | 1.0000 | 120 | — | **8.08%** |
| `bronze` 铜牌 | ≥ 50 单 或 ≥ ¥6,000 | 0.9833 | 118 | 2 | 6.53% |
| `silver` 银牌 | ≥ 200 单 或 ≥ ¥24,000 | 0.9667 | 116 | 4 | 4.92% |
| `gold` 金牌 | ≥ 500 单 或 ≥ ¥60,000 | 0.9500 | 114 | 6 | 3.26% |
| `diamond` 钻石 | ≥ 1000 单 或 ≥ ¥120,000 | 0.9417 | 113 | 7 | **2.40%** |

> 5 档全部可用（钻石 113 ≥ 保底线 112.68）。
> **注意钻石档余量只有 0.32 元**，成本稍高的商品会自动回落到金牌。

### 3.2 如果费率被证实是 3.5%（易支付），档位必须收紧

| 档位 | 专价 | 你净利率 | 能否用 |
| --- | --- | --- | --- |
| `retail` | 120 | 4.83% | ✅ |
| `bronze` | 118 | 3.28% | ✅ |
| `silver` | 117 | 2.48% | 🟡 极限 |
| — | 116 | 1.67% | ❌ |

> 只有 2–3 档、最多让 3 元。**销售赚不到差价，激励作用很弱。**
>
> **好消息**：保底公式会自动把不可用的档位挡掉，不会亏本。
> 但你需要重新调档位表（把 gold/diamond 的阈值调高或直接停用）。

### 3.3 档位是按「折扣率」定义的，不是固定价

因为每个商品成本不同，档位必须定义成**相对零售价的折扣**，而不是绝对金额：

```
bronze  折扣率 0.9833  （98.33 折 → 零售 120 时专价 118）
silver  折扣率 0.9667
gold    折扣率 0.9500
diamond 折扣率 0.9417
```

配合 §2.5 的保底公式，高价商品会自动被限制在能承受的档位。

### 3.4 一个战略选择：这 7 元怎么分配

你有 7 元的让价空间（120 → 113），但不必全给销售。三种分配方式：

| 方案 | 零售价 | 钻石专价 | 销售赚（卖130） | 你的净利率 |
| --- | --- | --- | --- | --- |
| A. 全给销售激励 | 120 | 113 | ¥17 | 2.40%–8.08% |
| B. 折中（推荐） | 118 | 112 | ¥18 | 2.0%–6.0% |
| C. 降价抢市场 | 114 | 108 | ¥22 | 约 3%–5% |

**建议先用 A（不改零售价），跑一个月看销量反应。**
如果发现价格是瓶颈（转化率低），再考虑 C。
**不要一上来就降价** —— 代充是刚需，客户更在意稳定和售后，不是差那几块钱。

## 四、数据模型

### 4.1 `price_tiers` 档位定义

```go
type PriceTier struct {
    ID   uint   `gorm:"primaryKey"`
    Code string `gorm:"size:32;uniqueIndex;not null"` // retail/bronze/silver/gold/diamond
    Name string `gorm:"size:64;not null"`

    // ---- 达成条件（满足任一即可）----
    MinMonthlyOrders int             `gorm:"not null;default:0"` // 近 30 天成功订单数
    MinMonthlyAmount decimal.Decimal `gorm:"type:numeric(14,2);not null;default:0"` // 近 30 天采购额

    // ---- 专价（相对零售价的折扣）----
    DiscountRate decimal.Decimal `gorm:"type:numeric(6,4);not null;default:1"` // 0.9833

    // ---- 保底与约束 ----
    MinMarginRate  decimal.Decimal `gorm:"type:numeric(6,4);not null;default:0.02"` // 最低净利率 2%
    MinRetailPrice decimal.Decimal `gorm:"type:numeric(12,2);not null;default:0"`   // MAP 最低零售价

    SortOrder int  `gorm:"not null;default:0"`
    Enabled   bool `gorm:"not null;default:true"`
    Remark    string `gorm:"size:255"`

    CreatedAt time.Time
    UpdatedAt time.Time
}
```

### 4.2 `listing_tier_prices` 商品级专价覆盖

有些商品的档位专价需要单独定（比如清库存的特价品）：


### 4.3 `buyers` 表新增字段

```go
// 当前专价档位（缓存，由 worker 每日重算）
PriceTier string `gorm:"size:32;not null;default:retail;index"`
// TierCalcAt 档位最近计算时间
TierCalcAt *time.Time
// TierGraceUntil 降级宽限截止时间（跌破条件后保留原档位到此时刻）

```

> 注意：**不需要** `commissions` / `withdraw_requests` / `commission_rules` 这三张表。
> 这是阶梯专价比返佣简单得多的地方。

## 五、档位计算与升降级

### 5.1 销量口径（关键设计）

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 时间窗 | **近 30 天滚动** | 不是永久累计，防止「冲一次量永久享受低价」 |
| 计入状态 | 仅 `delivered`（已发货） | 排除 `failed`/`cancelled`/`refunded` |
| 是否排除自购 | **是** | 防刷单冲档位 |
| 计算频率 | 每日 03:00（worker） | 不必实时，日更足够 |
| 判定条件 | 订单数 **或** 采购额，满足任一 | 不同商品客单价不同，双口径更公平 |

### 5.2 升降级规则

```
达到更高档条件 → 立即升级（次日生效）
跌破当前档条件 → 进入 7 天宽限期，宽限期内保留原档位
               → 宽限期满仍未达标 → 降级
```

**为什么要有宽限期**：销售某月冲量达标，下月月初回落，如果立刻降级会让他「不敢休息」。
7 天宽限让体验平滑，成本可控（7 天的让价总额有限）。

### 5.3 计算任务（worker）

```go
// task_tier_recalc  每日 03:00
func RecalcTiers(ctx context.Context) (Result, error) {
    // 1. 取所有 agent_status=1 的买家
    // 2. 聚合近 30 天 orders（delivered，排除自购）
    // 3. 按 min_monthly_orders / min_monthly_amount 匹配最高档位
    // 4. 对比当前档位：
    //      升级 → 立即改
    //      降级 → 若 tier_grace_until 未过则跳过，否则改
    // 5. 更新 buyers.price_tier / tier_calc_at
}
```

### 5.4 下单时如何用档位

```
BuyerQuote(listingID, qty, buyer):
  1. 取 buyer.price_tier（retail 则走原逻辑）
  2. 查 listing_tier_prices 是否有该档专价
     有 → 用该价
     无 → listing.sale_price × tier.discount_rate
  3. 保底校验：
       专价 ≥ 成本 × (1 + min_margin_rate)
       净利 = 专价 − 成本 − 专价 × fee_rate ≥ 零售价 × 2%
     不满足 → 自动回落到上一档（逐级回退到 retail）
  4. 返回最终单价
```

> **第 3 步的自动回落是必须的**：不同商品成本不同，
> 同一个档位对便宜商品可行、对贵商品可能亏本。
> 必须逐级回退，而不是整单失败。

## 六、防刷与风控

阶梯专价最大的风险是「**刷单冲档位**」——销售自己刷量到金牌，然后长期拿低价。

### 6.1 五道闸门

| # | 风险 | 检测 | 处理 |
| --- | --- | --- | --- |
| R1 | 自购冲量 | `order.buyer_id == 统计对象` 本身就是同一人 | 自购订单**不计入**档位统计 |
| R2 | 同人多账号 | 注册 IP / 登录 IP / 支付账户 相同 | 合并统计或标记可疑 |
| R3 | 刷单后退款 | 退款率 > 30% 且 ≥3 单 | 该批订单不计入统计 + 冻结档位 |
| R4 | 低价倾销 | 售价低于 `min_retail_price` | 警告 → 冻结代理资格 |
| R5 | 一次性冲量 | 单日订单占 30 天总量 > 50% | 标记复核，暂不升级 |

### 6.2 MAP 最低零售价

每档设 `min_retail_price`，写进代理协议：

```
零售 120，代理不得低于 120 对外销售（或按你的策略设 118）
违反 → 第一次警告，第二次冻结代理资格
```

> ⚠️ 技术上**无法强制**（他卖多少钱你管不到），只能靠协议 + 抽查 + 举报。
> 这是批发模式的固有代价，要提前接受。

### 6.3 禁止代理发展下级

**代理不得再发展下级代理并从下级拿差价。**

原因：一旦允许「代理 → 二级代理 → 三级」，就构成《禁止传销条例》里的
「层级 ≥ 三级 + 按发展人员计酬」，触传销红线。

**阶梯专价只能是「你 → 销售」的一级关系。**

## 九、关键设计决策汇总

| # | 决策 | 备选 | 理由 |
| --- | --- | --- | --- |
| D1 | **不做返佣，做阶梯专价** | 返佣 | 8.33% 毛利下返佣给不出钱 |
| D2 | 档位按**折扣率**定义 | 固定价 | 不同商品成本不同，折扣率可自适应 |
| D3 | 销量口径**近 30 天滚动** | 永久累计 | 防「冲一次量永久低价」 |
| D4 | 只统计 `delivered` 且**排除自购** | 全部订单 | 防刷单冲档位 |
| D5 | 降级有 **7 天宽限** | 立即降 | 平滑体验，成本可控 |
| D6 | 专价**自动逐级回落** | 整单失败 | 高成本商品可能承受不了低档位 |
| D7 | 保底**硬编码**（净利率 ≥ 2%） | 配置化 | 防运营误配亏光 |
| D8 | 代理资格**申请+审核** | 自动开通 | 早期只放信任的人 |
| D9 | 禁止代理**发展下级** | 允许 | 触传销红线 |
| D10 | MAP 最低零售价 | 不限制 | 防价格体系崩盘 |

### 验收标准

**功能**
- [ ] 销售下单按当前档位折扣正确算价
- [ ] 普通买家（`retail`）价格与改造前**完全一致**（硬要求，对比测试）
- [ ] 达到销量阈值后，次日自动升档
- [ ] 跌破阈值后，7 天宽限期内保留原档，期满降级
- [ ] 自购订单不计入档位统计
- [ ] 后台可手动改档位，立即生效

**保底**
- [ ] 专价低于成本时**拒绝生效**，自动回落到上一档
- [ ] 净利率低于 2% 时拒绝生效
- [ ] 后台配置低毛利商品的低档位时，界面标红警告

**防刷**
- [ ] 退款订单不计入销量
- [ ] 同 IP 多账号被标记
- [ ] 单日暴量（> 50%）触发复核

**回归**
- [ ] 现有 41 项 e2e 全绿
- [ ] 无销售资格的用户下单链路完全不受影响

## 十一、上线策略

**必须灰度**：

1. **先验证 0.25% 费率的真实性**（持牌？隐藏费用？结算周期？限额？）——见 §2.4
2. 做一笔真实小额交易，核对「到账 = 订单 × (1 − 0.25%)」，确认无隐藏扣费
3. 先只配 `retail` + `bronze` 两档，跑一周
4. 手动把 2–3 个信任客户设为 `bronze`，人工核对每笔价格
5. 确认无误后再开放 `silver` / `gold` / `diamond`
6. **销售资格一律后台人工开通**，V1 不做自助申请入口
7. 加一个总开关 `agent.enabled`，出问题一键关闭

## 十二、一句话总结

> **返佣是把你的毛利分给别人，阶梯专价是让别人赚他自己的差价。**
> 在 8.33% 的毛利下，前者最多只能给 ¥4.90/单，后者能让销售赚 ¥16–17。
>
> **你的 0.25% 费率是这套方案成立的关键**：
> 它让你在 8.08% 净利率下仍有 7 元的让价空间，能分出 5 档。
> 如果费率是 3.5%，只能分 2 档、让 3 元，方案价值减半。
>
> ⚠️ **但 0.25% 低于行业标准，上线前必须验证三件事**：
> ① 是否持牌机构（非二清） ② 是否含隐藏费用 ③ 结算周期与限额。
> 这三项任一有问题，都可能让「低费率」变成「高代价」。
