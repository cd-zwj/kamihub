# 04 · 安全、风控与通知

> 目标：从「出了事才知道」变成「有异常立刻知道」；从「谁都能刷」变成「有门槛」。
>
> 本篇含三块：**通知（P0）· 风控（P1）· 验证码与 2FA（P1）**。

---

## 一、通知系统（P0，1 天）

### 1.1 为什么这是 P0

kamihub 现在**没有任何主动通知**。这意味着下面这些事你都是「事后才知道」：

| 事件 | 现状 | 应该有 |
| --- | --- | --- |
| 16688 运营钱包余额不足 | 卖到没钱了才从失败订单发现 | 提前 2 天告警 |
| 某货源连续失败 | 买家投诉才知道 | 连续 3 次失败即告警 |
| 上游整体不可用 | 全店停摆时才知道 | 5 分钟内告警 |
| 卡单堆积 | 每天人工筛 | 超 10 分钟未发货即告警 |
| 对账出现差异 | 月底对账才发现 | 每日差异汇总 |
| 分销商异常刷单 | 佣金支出暴涨才发现 | 实时规则告警 |

**通知系统的价值不在「通知买家」，而在于「告警给自己」。**

### 1.2 设计：一个抽象的 Channel 接口

```go
// internal/notify/notify.go
type Level string

const (
    LevelInfo  Level = "info"
    LevelWarn  Level = "warn"
    LevelError Level = "error"
)

type Message struct {
    Level   Level
    Title   string
    Content string          // 支持简单 markdown
    Fields  map[string]any  // 结构化字段，便于前端渲染
    Link    string          // 站内跳转链接
    At      time.Time
}

// Channel 通知渠道。新增渠道 = 实现这个接口 + 注册，不动业务代码。
type Channel interface {
    Name() string
    Send(ctx context.Context, msg Message) error
}
```

内置渠道（按实现难度排序）：

| 渠道 | 优先级 | 说明 |
| --- | --- | --- |
| **Telegram Bot** | 🥇 先做 | 5 分钟接完，手机即时推送，最适合运维告警 |
| **Webhook** | 🥇 先做 | 通用，可接飞书/钉钉/企业微信机器人 |
| **站内信** | 🥈 | 后台「消息中心」页，留痕可查 |
| **邮件 SMTP** | 🥉 | 给买家发通知用，需要配 SMTP |

> **建议组合**：运维告警走 Telegram + Webhook（双通道，防漏）；
> 买家通知走站内信 + 邮件。

### 1.3 事件清单

#### A. 运维告警（发给自己）

| 事件 | 级别 | 触发条件 | 内容要点 |
| --- | --- | --- | --- |
| `balance.low` | 🔴 error | `platform.balance < 阈值` | 平台名、当前余额、日均消耗、预计可用天数 |
| `platform.down` | 🔴 error | 连续 3 次调用失败 | 平台名、错误信息、受影响货源数 |
| `supply.out_of_stock` | 🟡 warn | 库存从 >0 变 0 | 商品名、货源、平台 |
| `supply.check_failed` | 🟡 warn | `LastCheckOK=false` 连续 3 次 | 原因（下架/起购量/余额） |
| `order.stale` | 🟡 warn | `purchasing` 超 10 分钟 | 订单号、上游单号、卡在哪个阶段 |
| `order.fail_rate` | 🔴 error | 1 小时内失败率 > 30% | 失败原因 TOP3 |
| `reconcile.diff` | 🟡 warn | 对账发现差异 | 差异类型统计、金额合计 |
| `worker.task_failed` | 🟡 warn | 任务连续失败 2 次 | 任务名、错误 |
| `payment.notify_miss` | 🟡 warn | 支付单 30 分钟未收到回调 | 单号、金额 |

#### B. 买家通知（发给客户）

| 事件 | 渠道 | 内容 |
| --- | --- | --- |
| 下单成功 | 站内信 | 订单号 + 提货链接 |
| 发货完成 | 站内信 / 邮件 | 卡密 + 使用说明 + 提货链接 |
| 发货失败已退款 | 站内信 | 退款金额 + 原因（模糊化） |
| 余额变动（充值/佣金） | 站内信 | 金额 + 变动后余额 |

> ⚠️ **安全红线**：卡密**绝不要**发邮件/短信（易泄露、易被转发）。
> 邮件只发「提货链接」，卡密必须在站内页面查看。

#### C. 分销相关（发给自己 + 分销商）

| 事件 | 收件人 | 内容 |
| --- | --- | --- |
| 新分销商申请 | 自己 | 申请人 + 渠道 |
| 佣金可提现 | 分销商 | 金额 + 可提现日期 |
| 提现申请 | 自己 | 金额 + 账户（脱敏） |
| 异常刷单 | 自己 | 规则名 + 涉及账号 |

### 1.4 通知表

```sql
CREATE TABLE notifications (
  id           bigserial PRIMARY KEY,
  -- 收件人：内部告警为 NULL，买家/分销商为 buyer_id
  buyer_id     bigint,
  level        varchar(16) NOT NULL DEFAULT 'info',
  event        varchar(64) NOT NULL,
  title        varchar(255) NOT NULL,
  content      text,
  link         varchar(512),
  -- 投递状态
  read         boolean NOT NULL DEFAULT false,
  read_at      timestamptz,
  -- 各渠道投递结果
  channels     jsonb,          -- {"telegram":"ok","webhook":"fail: timeout"}
  created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_notif_buyer ON notifications (buyer_id, read, created_at DESC);
CREATE INDEX idx_notif_event ON notifications (event, created_at DESC);
```

### 1.5 防打扰设计（很重要）

否则第一周你就会把 Telegram 群刷爆然后关掉它：

| 机制 | 说明 |
| --- | --- |
| **同类聚合** | 同一 `event` 5 分钟内只发一次，累积数量合并（"余额不足告警 ×3"） |
| **静默期** | 夜间（如 02:00–07:00）只有 `error` 级别推送 |
| **去重键** | `event + 实体ID` 在窗口内去重 |
| **升级** | 同一问题持续 1 小时未恢复 → 提升级别重发一次 |

## 二、风控（P1，2 天）

### 2.1 为什么代充特别需要风控

代充是**高欺诈品类**，原因：

| 风险 | 后果 |
| --- | --- |
| 盗刷信用卡买卡密 | 持卡人拒付 → 你的支付通道被罚款/封停 |
| 跑分/洗钱 | 你的站被用作资金通道，账户被冻结 |
| 恶意退款/职业差评 | 毛利被吃光 |
| 批量注册刷优惠券 | 营销费用被刷爆 |
| 分销对刷套佣 | 佣金被套走 |

**最致命的不是单笔损失，是「支付通道被封」—— 那等于生意直接停摆。**

### 2.2 规则引擎设计（轻量，不做成 DSL）

不要上复杂的规则引擎（Drools 那类），kamihub 的量级用**规则表 + 顺序评估**足够：

```go
type RiskRule struct {
    ID       uint
    Code     string  // order_velocity / amount_anomaly / ip_blacklist / ...
    Name     string
    Scene    string  // register / login / order / withdraw / commission
    Enabled  bool
    Level    string  // pass(0) / review(1) / reject(2)
    Priority int
    Config   datatypes.JSON  // 规则参数，如 {"window":"10m","max":5}
    Action   string          // log / captcha / manual_review / reject
}
```

评估流程：

```
事件（如买家下单）
  → 按 Priority 取 Scene 匹配的启用规则
  → 逐条评估，命中即记 RiskHit
  → 汇总最高 Level：
       pass   → 放行
       review → 放行但标记，进人工队列
       reject → 拒绝
  → 写 risk_hits 表（无论结果都记，用于复盘）
```

### 2.3 P1 阶段的 8 条基础规则

| # | 规则 | 场景 | 阈值（建议初值） | 动作 |
| --- | --- | --- | --- | --- |
| R1 | 同 IP 注册频率 | register | 1 小时 > 3 个 | captcha → reject |
| R2 | 同 IP 下单频率 | order | 10 分钟 > 10 单 | review |
| R3 | 同买家下单频率 | order | 1 小时 > 20 单 | review |
| R4 | 单笔金额异常 | order | > 日均客单价 5 倍 | review |
| R5 | 日累计金额异常 | order | > 2000 元 | review |
| R6 | 退款率异常 | order | 近 30 天 > 30% 且 ≥3 单 | reject |
| R7 | 黑名单（IP/买家/收款账户） | 全部 | 精确匹配 | reject |
| R8 | 分销自购/互买 | commission | 见 `03` §5 | reject |

### 2.4 表结构

```sql
CREATE TABLE risk_rules (
  id         bigserial PRIMARY KEY,
  code       varchar(64) NOT NULL UNIQUE,
  name       varchar(128) NOT NULL,
  scene      varchar(32) NOT NULL,
  level      varchar(16) NOT NULL,   -- pass/review/reject
  priority   int NOT NULL DEFAULT 100,
  enabled    boolean NOT NULL DEFAULT true,
  config     jsonb NOT NULL DEFAULT '{}',
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE risk_hits (
  id          bigserial PRIMARY KEY,
  rule_code   varchar(64) NOT NULL,
  scene       varchar(32) NOT NULL,
  -- 主体：可能是 buyer_id / ip / order_no
  subject     varchar(128) NOT NULL,
  level       varchar(16) NOT NULL,
  action      varchar(32) NOT NULL,   -- log/captcha/manual_review/reject
  detail      jsonb,
  -- 人工处理
  reviewed    boolean NOT NULL DEFAULT false,
  reviewed_by bigint,
  reviewed_at timestamptz,
  review_result varchar(32),          -- allow / block
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_risk_subject ON risk_hits (subject, created_at DESC);
CREATE INDEX idx_risk_pending ON risk_hits (reviewed, created_at DESC);
```

### 2.5 黑名单

```sql
CREATE TABLE blacklist (
  id         bigserial PRIMARY KEY,
  kind       varchar(16) NOT NULL,   -- ip / buyer / phone / bank_account / email
  value      varchar(255) NOT NULL,
  reason     varchar(255),
  expires_at timestamptz,            -- NULL = 永久
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (kind, value)
);
```

> 黑名单必须支持**过期**。永久黑名单积累多了会误伤（共享 IP 场景）。

## 三、验证码（P1，0.5 天）

### 3.1 为什么需要

kamihub 现在只有限流。限流挡不住「慢速脚本」（每分钟 5 次，跑一整天）。
验证码是**成本不对称**的防线：真人 3 秒，脚本成本 ×100。

### 3.2 方案选择

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 自研图形码 | 无依赖 | 识别率高，基本没用 | ❌ |
| 滑块验证 | 体验好 | 需要前端配合 | 🟡 |
| **行为验证（点选/无感）** | 体验最好 | 需要第三方 | 🟡 |
| **极简算术/字符图** | 10 分钟实现 | 中等强度 | ✅ **P1 起步** |

**建议**：先上「自研简易字符码」（足够挡住 80% 的脚本），
等被针对了再换第三方（腾讯防水墙/极验/Cloudflare Turnstile）。

### 3.3 触发策略（不要全站都加，会掉转化）

| 场景 | 是否强制 |
| --- | --- |
| 注册 | ✅ 总是 |
| 登录失败 1 次后 | ✅ 是 |
| 下单 | 🟡 仅风控 `review` 命中时 |
| 查单 | ✅ 是（防遍历订单号） |
| 提现申请 | ✅ 总是 |
| 分销申请 | ✅ 总是 |

### 3.4 实现要点

- 验证码答案存 Redis，TTL 3 分钟，**一次性消费**
- 校验成功后立即删除，防重放
- 绑定 `session_id`（前端生成 UUID）而不是纯 IP（共享 IP 场景）
- 失败 3 次以上 → 临时封 `session_id` 15 分钟

## 四、TOTP 2FA（P1，1 天）

### 4.1 为什么必须做

kamihub 后台现在**只有一个密码**。管理员账号一旦泄露：

```
攻击者登入后台 → 看到所有平台凭证（虽然加密但能调用）
              → 可以给任意买家加余额
              → 可以改商品价格为 0
              → 可以导出卡密
```

**这是全站唯一的单点故障，比任何前端漏洞都严重。**

### 4.2 设计

| 项 | 方案 |
| --- | --- |
| 算法 | TOTP（RFC 6238），周期 30s，6 位数字 |
| 库 | `github.com/pquerna/otp/totp`（成熟、无额外依赖） |
| 绑定流程 | 生成 secret → 显示二维码（otpauth://）+ 明文 → 用户输入验证码确认 → 保存（加密） |
| 恢复码 | 生成 10 个一次性恢复码，**只显示一次**，哈希存储 |
| 强制范围 | `admin` 角色**强制**；`operator` 可选 |
| 免密登录 | 不做「记住此设备」（单店不需要，且降低安全） |

### 4.3 表结构

```sql
ALTER TABLE users ADD COLUMN totp_secret    varchar(255);  -- AES-256-GCM 密文
ALTER TABLE users ADD COLUMN totp_enabled   boolean NOT NULL DEFAULT false;
ALTER TABLE users ADD COLUMN totp_bound_at  timestamptz;

CREATE TABLE user_recovery_codes (
  id         bigserial PRIMARY KEY,
  user_id    bigint NOT NULL,
  code_hash  varchar(255) NOT NULL,
  used_at    timestamptz,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

### 4.4 登录流程改造

```
账号密码校验通过
  → totp_enabled?
      ├─ 否 → 直接签发 token（或强制引导绑定，若 role=admin）
      └─ 是 → 返回 {need_totp: true, ticket: <5分钟临时票据>}
                → 前端弹输入框
                → 校验 TOTP（或恢复码）
                → 签发 token
```

> **重要**：临时票据必须是**独立的一次性 token**，
> 不能把「已通过密码但未过 2FA」当作已登录状态，否则 2FA 形同虚设。

## 五、其他安全加固（顺手做，成本低）

| # | 项 | 说明 | 工作量 | 状态 |
| --- | --- | --- | --- | --- |
| S1 | 后台权限细化 | 加「角色-菜单」表，`operator` 只能看订单/发货，不能看平台凭证 | 0.5 天 | 未做 |
| S2 | 敏感操作二次确认 | 改平台凭证、人工调账、导出卡密 → 要求输密码 | 0.3 天 | ✅ 见 `18` |
| S3 | 登录通知 | 新 IP/新设备登录后台 → 发告警 | 0.2 天 | ✅ 见 `18` |
| S4 | 审计日志增强 | 现有 `AuditLog` 补齐「谁、什么时间、改了什么值（before/after）」 | 0.3 天 | 未做 |
| S5 | 导出限流 | 卡密导出、订单导出加频率限制 | 0.2 天 | 未做 |
| S6 | 密钥轮换预案 | 文档化 `ENCRYPTION_KEY` 轮换步骤（现在换了就解不开凭证） | 0.2 天 | ✅ 见 `17` |

> S6 值得特别说：kamihub 用 `ENCRYPTION_KEY` 加密平台凭证（AES-256-GCM）。
> **如果这个 key 丢了，所有上游凭证全部报废，只能重新录入。**
> 必须有「离线备份 + 轮换流程」的文档，否则这一天迟早出事。
>
> **落实结果**：不只是写文档 —— 密文加了密钥标签、支持双密钥过渡窗口、
> 并提供了 `keytool -mode rotate` 工具，换 key 变成一个可回滚的三步操作。
> 详见 `17-密钥轮换预案.md`。

## 六、优先级与依赖

```
P0  通知系统（Telegram + Webhook + 站内信）
      └─ 依赖：无。这是所有后续告警的基础，必须先做。

P1  验证码
      └─ 依赖：Redis（已有）
P1  风控规则引擎
      └─ 依赖：通知（命中要告警）
P1  TOTP 2FA
      └─ 依赖：无

P2  后台权限细化
      └─ 依赖：无
```

**顺序建议**：通知 → 2FA → 验证码 → 风控。
（先能看见问题，再堵最大漏洞，再防刷，最后精细化）

## 七、验收标准

### 通知
- [ ] 手动把某平台余额改成 0，5 分钟内收到 Telegram 告警
- [ ] 同一告警 5 分钟内只推一次（聚合生效）
- [ ] 02:00 的 `warn` 级别不推送，`error` 级别推送
- [ ] 站内信在后台消息中心可见、可标记已读

### 风控
- [ ] 规则可后台开关、改阈值，**无需重启**
- [ ] 同一 IP 连续注册 4 个 → 被拦
- [ ] 命中 `review` 的订单进人工队列且买家侧无感
- [ ] `risk_hits` 可按主体查询（用于申诉复核）

### 验证码
- [ ] 注册必须过验证码
- [ ] 验证码 3 分钟过期
- [ ] 同一验证码不能重复使用
- [ ] 失败 3 次后 session 被封 15 分钟

### 2FA
- [ ] admin 未绑 2FA 时被强制引导绑定
- [ ] 密码正确但 TOTP 错误 → **不能**拿到 token
- [ ] 恢复码只能用一次
- [ ] 临时票据 5 分钟失效

### 回归
- [ ] 现有登录/下单/发货全链路不受影响
- [ ] `go test ./...` 全绿
