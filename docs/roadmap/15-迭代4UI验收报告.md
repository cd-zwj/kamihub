## 三、4.3 图表看板：6 个图，全部真实数据

### 3.1 后端只加了 1 个接口

`GET /api/dashboard/charts?days=7|14|30` —— 一次返回 6 组数据。

**为什么合成一个接口**：看板是「一眼看全」的场景，6 个请求会让首屏出现 6 次闪烁与 6 次 loading。合成一个只查一次、渲染一次。

### 3.2 六个图（对应真实运营决策）

| # | 图 | 类型 | 回答什么问题 | 数据来源 |
| --- | --- | --- | --- | --- |
| C1 | 订单量与销售额趋势 | 双轴折线 | 生意在涨还是跌 | `orders` 按日聚合 |
| C2 | 订单状态分布 | 环形图 | 失败率是否异常 | `orders.status` |
| C3 | 货源成本对比 | 横向条形 | 哪家最便宜、该切哪家 | `supplies.cost_price` |
| C4 | 各上游成功率 | 进度条列表 | 哪个上游在恶化 | `orders` 按 `platform_id` |
| C5 | **每日采购消耗 + 预计可用天数** | 面积图 | **还有几天要充值** | `orders.total_amount` + `platforms.balance` |
| C6 | 商品销量 TOP 10 | 柱形 | 该重点补哪个货 | `orders` 按 `goods_id` |

**C5 是整页最值钱的图**：把「余额告警」变成「看得见的趋势」。

实测返回（真实库）：

```
days=14  daily=2  status=2  supplies=20  platforms=20
spend=2  balances=34  topgoods=10
avg_spend=437.45  total_balance=34000  days_left=77.72
```

即：日均消耗 ¥437、可用余额 ¥34000、按当前速度还能撑 **77 天**。

### 3.3 口径说明（写进代码注释，避免以后被误解）

- **销售额（gmv）** = Σ `paid_amount`，只统计 C 端订单
- **成本（cost）** = Σ `total_amount`（模型里已明确是成本口径）
- **毛利** = gmv − cost，只统计「两个数都有值」的 C 端订单
- 后台手工单（`channel=admin`）没有买家实付，**只计入订单量，不计入销售额/毛利** —— 强行算会得出负数

### 3.4 DataViz 原则落地

- 一个图只回答一个问题，没有塞三指标
- 颜色克制：主色 + 灰阶，红色只用于「异常」（`CHART_COLORS` 统一管理）
- 数字比图重要：关键指标用大字号 `Statistic` 放最上，图只做趋势
- **空数据一律显示 `Empty`，绝不画一片空白** —— `ChartEmpty` 组件统一处理

## 四、4.2 菜单分组 / 4.4 时间线 / 4.7 暗色 / 4.8 移动端

### 4.2 菜单：12 项平铺 → 4 组

```
概览
──────────
交易：订单 · 提货链接 · 在线支付
货源：上游商品 · 商品与货源 · 平台管理
运营：C 端商城 · 销售与专价 · 用户
系统：日志 · 安全与风控 · 访问令牌 · 使用准则 · 接口文档 · 系统设置
```

用 antd 的 `type:'group'`，**路由一行没动**，风险极低。

一个必须修的坑：菜单混入 group 节点后（没有 `key`、有 `children`），原来
`items.map(i => i.key)` 会拿到 `undefined`，导致高亮失效。已改成递归拍平取 key。

### 4.4 订单生命周期时间线

原来只列「每次货源尝试」，运营看不出订单卡在哪个阶段。现在合成一条完整时间线：

```
● 下单          10:23:01   单号 KM…
● 第 1 次尝试失败  16688 / SG…  业务错误  820ms
● 第 2 次尝试成功  17688 / SG…  210ms
● 发货完成      10:23:35   卡密 1 张 · 全程 34s
```

数据全部来自现有 `orders` + `order_attempts`，**不需要新表**。
三种终态都有对应节点：delivered / failed / purchasing（等待上游发货）。

### 4.7 暗色模式

- `ThemeProvider` 管理亮/暗，`localStorage` 记住选择，首次跟随系统偏好
- antd 组件用内置 `darkAlgorithm`（不自己调一套色板 —— 那是「做完整设计系统」的工作量，单店内部系统不需要）
- **关键工作量在 `styles.css`**：里面 20 多处硬编码 `#fff` / `#1a1f36` 等，暗色下会糊。
  已全部改成 CSS 变量（`--bg-page` / `--bg-card` / `--text-main` …），并加 `:root[data-theme='dark']` 覆盖组
- 顶栏加了切换按钮（太阳/月亮图标）

### 4.8 移动端：表格横向滚动已全量补齐

审查了 16 个含 Table 的页面，给 9 个缺 `scroll` 的全补上 `scroll={{ x: 'max-content' }}`，
共 19 处。这是「手机上 Table 溢出」的直接修法。

> 未做的：详情 Drawer 宽度自适应、工具栏按钮收进「更多」下拉、表单两列响应式。
> 表格滚动是手机上最痛的问题，先解决它；其余按需再补。

## 五、4.6 商品配置向导：未做，及原因

设计文档给的量是 **2 天**，且标 🟢 P2。本迭代的优先级排序是
「4.1+4.2+4.3+4.5 先做（收益 80%）」，向导排在最后。

这一项确实是 `05` 文档里唯一的 **P2 但强烈建议提前** 项，理由也很实在：
`Goods.tsx` 43KB，一个 Modal 塞了商品信息 + 货源 + 定价 + 卡密四件事，
**`MaxSupplyPrice` 漏填会导致亏本采购 —— 这是 UI 问题但后果是资损。**

不过它需要把 43KB 单文件拆成 `Steps` 向导 + 4 个子表单 + 实时成本校验，
是纯前端重构、改动面大、回归成本高。**建议单独排一轮做，不要混在 UI 主题改造里**
（`05` §七 的纪律第 1 条：每次只改一个页面，改完立刻验收）。
