### 1.3 缺失能力（实证）

**关键证据：`cmd/server/main.go` 中只有 HTTP server + 优雅关闭，没有任何 ticker。**

| 缺失 | 证据 | 影响 |
| --- | --- | --- |
| 后台定时任务 | `main.go` 无 `time.Ticker` / cron | 见下行各项 |
| 库存自动同步 | `SyncSupplyStock` 仅被 `handler_goods.go` 手工调用 | 超卖 |
| 超时支付单关闭 | `ExpireStale()` 定义在 `payment.go:599`，**无任何调用方** | 占库存 |
| 卡单自动补偿 | `RetryQuery` 仅被 `handler_order.go:236` 手工调用 | 客服压力 |
| 对账 | 无 | 资损 |
| 通知/告警 | 无（只有提货页展示联系方式） | 盲飞 |
| 风控 | 仅 `textfilter` + 限流 | 欺诈风险 |

| 2FA | 无 | 后台单密码 |

## 三、差距的本质：三层分类

把上面的差距按「性质」重新归类，这直接对应实施计划的三个阶段：

### 第 1 层：运营安全（不做会出事）

- 定时任务 / 库存同步 / 超时关单 / 卡单补偿
- 对账
- 通知告警

**特征**：不影响功能可用性，但会导致资损、超卖、口碑崩塌。
**结论**：**最高优先级**，且改造风险最低（纯新增，不动现有业务逻辑）。

### 第 2 层：风险防护（不做会被打）

- 风控规则引擎
- 验证码
- TOTP 2FA
- 后台权限细化（轻量）

**特征**：出事前感觉不到，出事后损失巨大（支付通道被封 = 生意停摆）。
**结论**：P1，在第 1 层稳定后立刻做。

### 第 3 层：增长与体验（不做赚得慢）

- 分销
- 会员等级 / 优惠券
- 报表
- UI 改造

**特征**：直接关联收入，但依赖前两层稳定。
**结论**：分销优先级最高（P0 中的最后一项），其余 P2。

> ⚠️ **注意一个反直觉的排序**：分销虽然是「赚钱的」，但我把它放在第 1、2 层之后。
> 原因：分销会带来**大量外部流量和外部账号**，如果风控和对账没做好，
> 分销商会成为刷单、洗钱、套佣金的入口，反而放大风险。
> **先能安全地收钱，再谈规模化收钱。**

## 四、kamihub 相比独角数卡的三个真实优势（别丢）

升级过程中要保住这些，它们比独角数卡做得更好：

| 优势 | 说明 |
| --- | --- |
| **两阶段采购的边界** | 「下单成功后再也不换货源」这条规则，独角数卡没有这么明确的隔离 |
| **钱包冻结/结算模型** | `frozen → settled/refunded` 三态，配合 `request_id` 唯一索引，防重复扣款很扎实 |
| **16688 签名实现 + 对拍测试** | 用 Node 参考实现做交叉验证，这段是硬资产 |

**升级原则：加新能力，不改这三处的语义。**

---

## 五、结论

1. kamihub 的**核心交易链路已经成熟**，不需要重写采购/路由/发货。
2. 缺的全部集中在**外围**：调度、对账、告警、风控、增长、UI。
3. 独角数卡 35 个模块里，真正值得搬的只有 **10 个**，另有 **11 个**可借思路。
4. 优先级严格按「运营安全 → 风险防护 → 增长体验」推进，不要倒序。
