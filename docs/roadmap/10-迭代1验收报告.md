## 四、过程中发现并修复的一个真实缺陷

### 问题：mock 适配器跨请求丢失订单

**现象**：卡单补偿任务能识别出卡单（"卡单 1 笔"），但补发始终失败：

```
POST /api/orders/19/retry
→ {"code":0,"msg":"模拟平台未找到该订单 (上游: MOCK_NOT_FOUND)"}
```

**根因**：`PlatformService.ClientByID()` 每次调用都会 `BuildClient()` →
`factory.Build()` 构造一个**全新的 Client 实例**，而 mock 的订单存在
`Client.orders` 实例字段里。于是：

```
下单时的 Client 实例 A  →  orders["MOCK..."] = 结果
查单时的 Client 实例 B  →  orders 是空 map  →  MOCK_NOT_FOUND
```

**为什么之前没暴露**：e2e 从不在「下单」之后跨请求查单 ——
采购链路在一次请求内完成（下单→轮询→发货），用的都是同一个实例。

**修复**：把订单存储提到包级，按平台 ID 隔离共享：

```go
type orderStore struct {
    mu     sync.Mutex
    orders map[string]*platform.PurchaseResult
    hits   map[string]int
}
var (
    storeMu sync.Mutex
    stores  = map[uint]*orderStore{}
)
func storeFor(platformID uint) *orderStore { /* 取或创建 */ }
```

`Client` 改为持有 `store *orderStore`，不再持有自己的 map。

**为什么这是正确的修复方向**：真实上游（16688）是**服务端有状态**的 ——
订单存在它那边，客户端无状态。mock 作为「假上游」，必须模拟这一点，
否则卡单补偿、对账这类**跨请求链路**在本地根本没法验证。

> 注意：这个修复只影响 mock 适配器（本地联调/测试专用），
> 不改变任何生产链路行为。真实适配器本来就是无状态 HTTP，无需缓存。

## 五、设计要点回顾

### 5.1 为什么用 `time.Ticker` 而不是 asynq

当前量级（376 单累计、单实例）用不到 asynq 的分布式抢任务与持久化重试。
代价是要求任务必须幂等 —— 这样将来换 asynq 只是换调度器，任务函数一行不改。

**升级信号**：出现多副本部署，或需要「任务绝对不能丢」时再换。

### 5.2 为什么任务要加 advisory lock

`pg_try_advisory_lock` + `db.Connection()` 把连接钉住（会话级锁必须同连接加解锁），
保证多实例部署时同一时刻只有一个实例跑同一个任务。

### 5.3 为什么告警要聚合 + 静默期

没有聚合，第一周就会把 Telegram 群刷爆，然后运维关掉通知 —— 等于没有。
静默期只放 `error`，避免半夜被 `warn` 吵醒。

### 5.4 为什么对账第一版只检测不改库

订单状态不一致可以以上游为准自动修，但**钱包差异不行** —— 钱的事必须人工确认。
先跑两周确认无误报，再逐项开启自动修复。

### 5.5 卡单补偿的铁律

**只查单，绝不换源重下。** 上游单号已存在说明款可能已扣，
换一家买就是重复扣款。这与 kamihub 原有的两阶段采购边界一致。
