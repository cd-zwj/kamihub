## 二、核心实现：保底公式与逐级回落

### 2.1 保底公式（硬编码，不配置化）

```
下限 = max(
    成本 × (1 + 2%),                            // ① 防亏本
    (成本 + 零售价 × 最低净利率) / (1 − 费率)      // ② 防手续费吃光
)
```

两个 `max` 分支对应两种不同的亏损方式，**少任何一个都会在极端参数下漏出亏本单**：

- 只有 ① 时：高费率下「卖价 > 成本」但手续费吃光利润 → 亏
- 只有 ② 时：费率很低时下限可能低于成本 → 亏

按设计文档基准（成本 110 / 零售 120 / 费率 0.25%）验算：

```
① = 110 × 1.02 = 112.20
② = (110 + 120×0.02) / 0.9975 = 112.40 / 0.9975 = 112.6817
下限 = 112.6817
```

与文档 §2.5 的 112.68 一致，已由 `TestFloorPriceMatchesDesignDoc` 固定。

### 2.2 硬编码下限：最低净利率不得低于 2%

档位表里有 `min_margin_rate` 字段，但实际生效值 = `max(字段值, 2%)`。

理由（设计 D7）：允许运营把净利率配到 0，等于允许一次配置失误把全站卖成亏本。这个风险不值得用「灵活性」换。后台改到 2% 以下会被直接拒绝（`TestUpdateTierRejectsRetailDiscount`）。

### 2.3 逐级回落（设计 D6）

```
买家当前档位 → 算价 → 过保底？
  过 → 成交
  不过 → 沿「折扣率从高到低」往前走一档（更贵）→ 再算 → ...
  最差一定落在 retail（原价）
```

为什么必须回落而不是整单失败：**不同商品成本不同**，同一档位对便宜商品可行、对贵商品可能亏本。

实测证据（`verify-tier.mjs`）：

```
PASS 成本 111 时钻石档自动回落（不回落到 113）  -- tier_price=114 tier_code=gold
PASS 回落标记已置位  -- fell_back=true
```

钻石档 113 在成本 111 时净利约 1.7 元（1.5%）< 2% 保底 → 自动回落到金牌 114。这正是设计文档说的「钻石档余量只有 0.32 元，成本稍高的商品会自动回落」。

### 2.4 一个额外的安全默认：未录成本的商品只在 retail 成交

上游商品常见「没录成本价」。此时 `cost = 0`，保底公式会算出 0 下限，任何折扣都能过 —— 等于拿未知风险赌博。

所以实现里加了一条：**成本为 0 且非 retail 档 → 一律回落**（`TestNoCostPriceFallsBackToRetail`）。

## 三、retail 路径为什么「结构上」不可能变价

验收门有一条硬要求：**普通买家价格必须与改造前完全一致**。

实现上不是「算对了」，而是**结构上不经过任何计算**：

```go
func (s *PricingService) PriceFor(...) {
    if tier.IsRetail() {
        return listing.SalePrice, nil   // 直接返回，不做任何乘法
    }
    ...
}
```

而 `BuyerQuote` 在 `buyerID == 0` 或 `pricing == nil` 时连 `Quote()` 都不进，直接 `unitPrice = row.SalePrice`。

另外 `retail` 档的折扣率被**锁死为 1**（`UpdateTier` 拒绝修改），且**不能被停用**（它是所有回落路径的兜底）。

三重保证 + 两个用例（`TestRetailPriceIdenticalToBefore`、`verify-tier.mjs` 第 3 项）盯着它。

## 四、档位重算（worker）

### 4.1 统计口径

| 项 | 决定 |
| --- | --- |
| 窗口 | 近 30 天滚动（设计 D3，防「冲一次量永久低价」） |
| 计入状态 | 仅 `delivered` |
| 金额 | `paid_amount` 实际支付额 |
| 判定 | 订单数 **或** 金额，满足任一（双口径更公平） |
| 频率 | 每 24 小时（日更语义，实时算没意义） |

### 4.2 升降级

- 达到更高档 → 立即升级
- 跌破当前档 → 进 7 天宽限期，期满才降级（设计 D5）

### 4.3 防刷闸门

| 闸门 | 实现 |
| --- | --- |
| R3 退款率过高 | 窗口内退款率 > 30% 且订单数 ≥ 3 → **本次不予升级** |
| R5 单日暴量 | 单日最高订单数占窗口总量 > 50% 且总量 ≥ 20 → **本次不予升级** |

实测：`TestTierRecalcRefundRateBlocksUpgrade`（50 单 delivered + 50 单 refunded = 50% 退款率 → Held=1，不升级）。

### 4.4 ⚠️ 关于设计文档 R1「自购订单不计入统计」的偏差

设计文档 §6.1 R1 写的是「自购订单不计入档位统计」。**这条在批发模式下不成立**：

R1 是**返佣模式**的规则（防止上级买自己的货套佣金）。本项目是批发模式 ——
销售本来就是「从我这拿货再卖出去」，他自己的下单就是业务本身。
如果排除自购，**所有人销量都是 0，整个档位系统直接失效**。

所以实现里**不排除自购**，防刷改由 R3（退款率）+ R5（暴量）承担。这是刻意的，不是漏做。

## 九、遗留

1. **同 IP 多账号（R2）未做**：需要 IP 聚类或设备指纹，属独立工作量。当前只靠风控模块的「同 IP 注册频率」规则做粗筛。
2. **后台配置时的实时预警未做**：现在只能在专价目表看到「已回落」，不能在改档位那一刻就提示「这个档位对该商品不成立」。建议补一个「按当前商品成本批量预检」的按钮。
3. ~~销量统计折线图~~ —— **已补做**（见 `16-收尾批次验收报告.md` §四）：用零依赖的内联 SVG（Sparkline），刻意不引 recharts，避免把它拉回商城主包。
4. **`PAY_FEE_RATE` 必须先实测**：所有保底计算都依赖它。上线前务必做一笔真实小额交易核对到账金额 = 订单 × (1 − 费率)。**如果实际费率是 3.5%，保底公式会自动收紧档位（不会亏本），但阶梯会从 5 档变成 2 档，需要重新调档位表。**
5. **灰度策略**（设计 §11）必须遵守：先只开 retail + bronze 跑一周 → 手动给 2–3 个信任客户 → 人工核对每笔价格 → 再放开高档位。
