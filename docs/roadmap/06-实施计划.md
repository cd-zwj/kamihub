## 零、前置条件（必须先完成，否则后面全是坑）

### P0-1 · `git init` + 基线跑通（0.5 天）🔴 最高优先

## 五、迭代 3 · 销售阶梯专价（3 天）🔴 P0（业务核心）

详细设计见 `03-销售阶梯专价设计.md`。

> ⚠️ **重要变更（v1.4）**：不做返佣分销，改做**按销量拿专价**的阶梯批发价体系。
> 原因：成本 110 / 售价 120（毛利率 8.33%），返佣最多只能给 ¥4.90/单，没人会做；
> 而阶梯专价让销售自己赚差价（¥16–17/单），你的毛利按档位锁定。
> 工作量 3 天，不碰主交易链路。

### 方案对比（为什么是阶梯专价）

| | 返佣 | 阶梯专价 |
| --- | --- | --- |
| 你能给销售最多 | ¥4.90（再给就归零） | 让价 ¥7（专价 120→113） |
| 销售实际能赚 | ¥1–4.9 | **¥16–17**（自己加价） |
| 你的毛利 | 越卖越薄 | **按档位锁定** |
| 开发量 | 6.5 天 | **3 天** |
| 改动现有代码 | `shop_order.go`（资损高危） | `listing.go` 一个函数 |
| 结算/提现/冲正 | 全部要写 | **不需要** |

### ✅ 前置条件已满足：你的费率 0.25%

| 费率 | 零售净利率 | 最大让价 | 可分档数 |
| --- | --- | --- | --- |
| **0.25%（你的）** | **8.08%** | **7 元（120→113）** | **5 档** |
| 0.6%（官方） | 7.73% | 7 元 | 5 档 |
| 3.5%（易支付） | 4.83% | 3 元（120→117） | 2 档 |

> **0.25% 完全支持 5 档阶梯，不需要先换通道。**
>
> ⚠️ 但上线前要验证这个费率：① 是否持牌机构（非二清）
> ② 是否含隐藏费用 ③ 结算周期与限额。详见 `03` §2.4。

## 七、跨迭代的工程纪律

### 7.1 分支策略

```
main        ← 生产分支，只有通过验收才合并
  └─ feat/worker-mode
  └─ feat/notification
  └─ feat/agent-tier
  └─ feat/ui-theme
```

- 一个迭代一个或多个 `feat/*` 分支
- 合并前必须：`go test ./...` 绿 + e2e 绿 + 自测通过
- **禁止直接在 `main` 上开发**

### 7.2 提交规范

```
feat(worker): 新增库存同步定时任务
fix(order): 修复卡单补偿重复查单
refactor(platform): 抽取 HTTP doer 重试逻辑
docs(roadmap): 补充销售档位设计
test(agent): 覆盖专价低于成本的自动回落
```

### 7.3 测试要求（每个迭代）

| 类型 | 要求 |
| --- | --- |
| 单元测试 | 新增业务逻辑覆盖率 ≥ 70% |
| 集成测试 | 涉及 DB 的必须有（kamihub 已有此惯例） |
| e2e | 现有 41 项必须全绿，新增功能要加用例 |
| 手工验收 | 每个迭代的「验收门」逐条打勾 |

### 7.4 数据库变更纪律

kamihub 用 `AutoMigrate`。这很方便但**很危险**（可能悄悄改列类型）。

**规则**：
1. 只允许**加表、加列**（可空或带默认值）
2. **禁止**删列、改列类型、改约束
3. 每个迭代上线前在**生产数据副本**上跑一次迁移，确认无损
4. 上线前完整备份（`pg_dump` + 校验和）

### 7.5 发布流程（每次上线）

```
1. 备份数据库（pg_dump，验证 checksum）
2. 本地跑全量 e2e
3. 构建镜像，先在测试容器起一遍
4. 择低峰期部署（建议 03:00–06:00）
5. 部署后立刻验证：/health、下一单真实订单、看 worker_task_runs
6. 观察 30 分钟
7. 出问题 → 回滚（见 §8）
```

## 八、风险与回滚

### 8.1 风险清单

| 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- |
| 定时任务打爆上游限流 | 中 | 上游封 API | 首版频率调保守（库存 5min 起）；严格按 `RateLimitPerMin` 控并发 |
| 对账自动改库改错 | 中 | 数据错乱 | **第一版只检测不改库**；自动修复需人工开关 |
| 专价配错导致亏本 | 中 | 资损 | 保底公式 + 自动逐级回落；灰度 + 前 10 笔人工核对 |
| `listing.go` 改价逻辑出错 | 中 | 定价错误 | 对比测试：普通买家价格必须与改造前完全一致 |
| AutoMigrate 改坏数据 | 低 | 生产事故 | 只加不改 + 副本预演 + 备份 |
| 2FA 把管理员锁在门外 | 低 | 无法登录 | 恢复码 + 数据库手工重置预案 |
| 前端 build 产物与后端不匹配 | 中 | 页面白屏 | 迭代 4 的 embed 方案可根治 |
| GPL 污染 | 低 | 法律风险 | 只学思路，代码全部独立实现，review 时确认 |

### 8.2 回滚策略

| 场景 | 回滚动作 | 耗时 |
| --- | --- | --- |
| 前端问题 | 回退 dist / `git revert` UI 提交 | 5 分钟 |
| 后端逻辑问题 | `git revert` + 重新构建部署 | 15 分钟 |
| worker 问题 | 停 worker 容器，api 不受影响 | 1 分钟 |
| 数据库迁移问题 | 恢复备份 | 30 分钟 |
| 销售档位出错 | 关闭功能开关（`agent.enabled`） | 1 分钟 |

> **强烈建议**：销售、通知、风控都加一个**总开关**（`settings` 表配置），
> 出问题一键关掉，不用回滚代码。这是最实用的运维保险。

## 十、如果只做一件事

如果时间或预算只够做一件事，**做迭代 1（运维地基）**。

理由：
- 它是唯一「不做就会持续漏钱」的部分（超卖、资损、卡单、余额耗尽）
- 它风险最低（纯新增，不动交易链路）
- 它是后面所有功能的基础（对账要定时器、档位要库存准、告警要通知）

**阶梯专价可以晚一周，超卖不能多一天。**

## 十一、一个必须说的前提

**毛利率 8.33%（110 进 120 卖）仍然偏薄，但你的 0.25% 费率已经解决了一大半问题。**

按这个数字：
- 支付手续费只吃掉 **3%** 的毛利（0.25% × 120 = ¥0.30）
- 净利率 **8.08%**（对比易支付 3.5% 时只有 4.83%）
- 仍有 7 元让价空间可分 5 档

**但这仍然是个薄生意**：一次 5% 的退款率、一次上游涨价，就会吃掉大半利润。
所以除了功能计划，仍建议继续优化：

| 方向 | 说明 | 影响 |
| --- | --- | --- |
| **降采购成本** | 成本从 110 降到 105，毛利从 10 涨到 15（+50%） | ⭐⭐⭐ 最有效 |
| ✅ 低费率通道 | 你已是 0.25%，**这块已经做到位了** | — |
| 提售价 | 120 → 125，但要看竞品 | ⭐⭐ 有天花板 |
| 做高毛利品 | 找毛利率 ≥ 15% 的 SKU（可开更宽阶梯） | ⭐⭐ 需要选品能力 |
| 提高复购 | 月付刚需，复购是最大利润来源 | ⭐⭐⭐ 被低估 |

> **一句话**：你的费率结构已经很好了，**剩下能拉利润的只有「降成本」和「提复购」**。
> 前者靠选货源，后者靠产品体验和售后 —— 这两件事比任何功能都值钱。
