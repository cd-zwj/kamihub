## 一、S4 解决什么问题

### 改之前的状态

审计日志有 `action`、`target_type`、`target_id`、`detail` 四个字段，
但**绝大多数调用把 `detail` 传成 `nil`**：

```go
h.auditLog(c, "settings.update", "setting", key, nil)   // 改了哪个值？不知道
h.auditLog(c, "platform.update", "platform", p.Name, nil)
h.auditLog(c, "goods.update", "goods", g.Code, nil)
```

于是日志只能回答「**有人在某个时间改了设置**」，回答不了
「**改的是哪个字段、从什么改成什么**」。

### 这个缺口在实际中长什么样

> 某天发现定价不对，一批订单少赚了。想知道「昨天是不是把某个设置改错了？」
> 打开审计日志 —— 只有 `settings.update · setting · security` 一行。
> security 里有 20 多个字段，到底动了哪个，完全看不出来。

同类场景：忘了自己把哪个档位的折扣调过、把某个商品的成本价改错过、
把提货链接默认有效期从 7 天改成了 1 小时。

**这类问题跟「有几个人」无关** —— 单人也一样会想不起来。
所以 S1（防别人）可以等，S4（帮自己回忆）不能等。

## 二、怎么做的

### 2.1 只记真正变化的字段

前端每次保存都会提交整个 JSON 对象（包括没动过的字段）。
如果全量记录，「改了一个数字」会被淹没在二十个未变字段里，反而看不见重点。

所以每次写审计前先算差量：

```go
before := service.Snapshot(旧记录)
after  := service.Snapshot(新记录)
h.auditChange(c, "settings.update", "setting", key, before, after)
```

落库结构（仍是 `audit_logs.detail` 这一列，**没有改表结构**）：

```json
{
  "changed": [
    { "field": "jwt_ttl_hours", "before": 12, "after": 24 }
  ]
}
```

只发生变化的字段才出现。内容完全相同的保存会记成 `{"changed":[]}` ——
这本身也是有意义的信息（「他保存了但什么都没改」）。

### 2.2 敏感字段只记「改过」，不记值

这是这次改动里**最不能出错的地方**。

如果审计日志把商户密钥、平台凭证、密码记进去，
它自己就变成了一个「所有后台账号都能看的明文密钥库」—— 比不记更糟。

处理方式：命中敏感规则的字段只留字段名 + `masked: true`：

```json
{ "changed": [ { "field": "key", "masked": true } ] }
```

敏感判定（`IsSensitiveField`）两层：

| 层 | 内容 | 为什么 |
| --- | --- | --- |
| 精确名 | `key` `secret` `pkey` `password` `token` `credentials` `api_key` `apikey` `api_secret` `app_secret` `secretkey` `merchant_key` `webhook_secret` | 已知字段 |
| 后缀 | `_key` `_secret` `_password` `_token` `_apikey` `_pwd` | 以后新增 `notify_key`、`secondary_secret` 也不会漏 |

**刻意取「宁多遮不漏」**：多遮一个非敏感字段，最多少一条追查线索；
漏掉一个密钥，等于把密钥写进了所有后台账号都能看的地方。

反过来，这些**明确不遮**（遮了反而丢失追查能力）：
`app_id` / `pid`（商户号，要能看出改的是哪个商户）、
`enabled`、`discount_rate`、`jwt_ttl_hours`、`api_url`、`credentials_changed`。

### 2.3 完全不进审计的字段

```go
var auditSkipFields = map[string]bool{
    "id": true, "created_at": true, "updated_at": true,
    "password_hash": true, "totp_secret": true, "device_hash": true,
}
```

前四个每写一次都会变，记下来只有噪音；
后三个属于「连『变没变』都不该留痕」的类别。

### 2.4 一个必须处理的数字陷阱

`before` 来自 Go 结构体（`int`、`int64`），`after` 来自 JSON 解析（`float64`）。

如果直接 `reflect.DeepEqual`，`12`(int) 和 `12`(float64) 会被判为不同 ——
于是**每次保存都会刷出一条假的「改了 jwt_ttl_hours」**，而且 `before: 12, after: 12` 看起来像鬼打墙。

所以比较前先做数字归一化（`toFloat`）。有专门的用例守这一条：
`TestDiffFieldsIgnoresNumericTypeDifference`。

但「一边数字一边字符串」（`12` vs `"12"`）仍算不同 —— 类型变了就是变了。

### 2.5 `json:"-"` 字段天然进不了审计

`Snapshot()` 走一次 JSON round-trip 而不是反射读字段，
所以 `Platform.Credentials`（`json:"-"`）自动被排除 —— 不需要额外白名单。

代价是「凭证被换过」这个事实也丢了，所以平台更新处额外加一个布尔标记：

```go
before["credentials_changed"] = false
after["credentials_changed"]  = true   // 本次传了新的凭证
```

### 2.6 覆盖到哪些动作

| 动作 | 为什么必须记差量 |
| --- | --- |
| `settings.update` | security / payment 改错直接漏钱，且字段多达 20+ |
| `platform.update` | 改网关地址、超时、凭证都会改变采购行为 |
| `goods.update` | 改售价、成本价、库存模式 |
| `listing.update` | 改 C 端售价与是否上架 |
| `agent.tier_update` | 折扣率改一个点就是全线价格变动 |
| `risk.rule_update` | 阈值调松调紧直接影响误拦率 |
| `user.update` | 改角色、禁用账号 —— 追责场景最需要 |

## 三、前端

「日志」页的审计 Tab，「详情」列从 `JSON.stringify(detail)` 改为结构化展示：

```
notice  ~~E2E 测试提示：请在 24 小时内联系客服。~~ → S4 差异检查 mvhzod4e
key     [已修改（敏感值不记录）]
```

- 老记录（没有 `changed` 结构）退回显示原始 JSON，不会崩
- 超过 4 个字段时显示「另有 N 个字段」，避免撑爆行高
- `masked` 用橙色 Tag 明确标注原因，而不是显示成空白让人困惑

## 五、一个真实的小插曲（值得记下来）

真机验证时我用 PowerShell 直接 `Invoke-RestMethod` 提交中文，
没有显式 UTF-8 编码，结果 `site_name` 被写成了 `"????"`。

发现之后改回 `"测试商城"` —— 而这次修复**被审计日志完整记了下来**：

```json
{ "field": "site_name", "before": "????", "after": "测试商城" }
```

这恰好是 S4 的价值演示：改了什么都留痕，
连「我自己改错了、又改回来」都留痕。附带也是给运维的提醒：
**用脚本调接口时中文必须显式 UTF-8 编码**，否则写进库的是问号。
