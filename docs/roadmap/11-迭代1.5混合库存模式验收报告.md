# 迭代 1.5 验收报告：混合库存模式（Hybrid Stock Mode）

> 目标：让「上游代发」商品的退货卡密重新变成可售库存，同时不破坏既有的上游采购链路。
> 关联文档：`06-实施计划.md`（迭代 1 之后插入的小迭代）、`08-术语与业务口径.md`。

---

## 一、要解决的问题

自建卡网里有一类真实的资损：

1. 商品是「上游代发」（`stock_mode=1`），买家下单 → 系统去上游买 → 发卡。
2. 买家退款 / 撤单，卡密被退回卡密池（`card_stocks.status=0`）。
3. 但这张卡密**永远卖不出去** —— 因为商品的供货方式是「只走上游」，
   `OrderService.Create` 里 `if goods.IsLocalStock()` 这个分支根本不会命中它。

结果：池子里堆着一批已经付过钱的卡密，前台却还在花钱去上游买同一件东西。
每退一单就沉一笔资金。

### 为什么不能简单「两种模式都试一下」

最直觉的做法是「先发池子、池子不够再发上游」。但一条订单如果一半来自池子、
一半来自上游，一旦上游那半失败：

- 退款金额算多少？
- 作废范围包括哪些卡密？
- 已经发给买家的池子卡密要不要追回？

三个问题都说不清。所以本迭代的硬约束是：

> **一笔订单只从一个通道取货，绝不拆单。**

## 二、实现内容

### 2.1 数据模型（`backend/internal/models/goods.go`）

```go
const (
    StockModeUpstream = 1 // 只走上游
    StockModeLocal    = 2 // 只用卡密池
    StockModeHybrid   = 3 // 卡密池 + 上游（新增）
)

// 混合模式下卡密池是否优先
LocalStockFirst bool `gorm:"not null;default:false" json:"local_stock_first"`
```

新增三个谓词，把「能不能吃池子」和「能不能走上游」区分开：

| 方法 | mode=1 | mode=2 | mode=3 |
|---|---|---|---|
| `IsLocalStock()` | false | true | false |
| `IsHybridStock()` | false | false | true |
| `UsesCardPool()` | false | true | **true** |
| `UsesUpstream()` | true | false | **true** |

`IsLocalStock()` 保持原语义（只吃池子），新代码一律用 `UsesCardPool()` /
`UsesUpstream()` 判断「通道是否可用」。

### 2.2 取货编排（`backend/internal/service/order.go`）

`Create` 拆成三层，原来那一大段上游逻辑原样搬进 `createFromUpstream`：

```
Create()            —— 校验、幂等、加锁、分流
  ├─ dispatch()     —— 按 stock_mode 选通道
  │    ├─ local  → createFromCardPool()
  │    ├─ hybrid → createHybrid()
  │    └─ 其余   → createFromUpstream()
  ├─ createFromCardPool()  —— 建订单 + deliverFromPool(reused=false)
  └─ deliverFromPool()     —— 把卡密发到「已存在的订单」上
```

`createHybrid` 的判定抽成纯函数 `planHybrid`，便于穷举测试：

| 优先级 | 池子够不够 | 首选 | 兜底 |
|---|---|---|---|
| 池子优先 (true) | 够 | 卡密池 | 无 |
| 池子优先 (true) | 不够 | 上游 | 无（整单上游） |
| 上游优先 (false) | 够 | 上游 | **失败退回池子** |
| 上游优先 (false) | 不够 | 上游 | 无 |

### 2.3 兜底必须复用原订单（关键细节）

上游优先且上游失败时，`createFromUpstream` **已经落了一笔失败订单**
（同一个 `request_id`）。此时若新建一笔池子订单：

- `orders.request_id` 唯一索引冲突；
- `isDuplicateKey` 分支会 `findByRequestID` 回放到那笔**失败**订单；
- 买家「钱扣了、货没拿到」。

所以抽出 `deliverFromPool(order, ..., reused=true)`：把卡密发到原订单上，
让它从 `failed` 变 `delivered`，并**保留 `attempts`**（上游试过几次是排查线索）、
清掉 `error_msg` / `error_kind`。

池子也兜不住时，两条失败原因都要留下：
`"上游采购失败（…）；卡密池兜底也不足：…"`。

### 2.4 库存合并（`backend/internal/service/listing.go`）

新增 `supplyStockByGoods()`，批量汇总各商品启用中货源的库存缓存。三个刻意设计：

1. **批量查**，避免列表页 N+1。
2. **负库存不算进求和**：上游用 -1 表示「不限/未知」，把它当数字加会得出无意义的负数；
   只要有一条是 -1，整个商品的合并库存就报 -1。
3. **时间取最旧**，不取最新：展示的库存是各货源之和，整个数字的可信度取决于
   最陈旧的那部分；取最新只会制造虚假的新鲜感。

C 端 `ShopListing` 新增两个字段：

| 字段 | 含义 |
|---|---|
| `stock_exact` | 库存是否精确。纯卡密池（或混合但无货源）为 `true`，含上游缓存为 `false` |
| `stock_updated_at` | 上游库存缓存最旧的同步时间，纯卡密池为 `null` |

后台 `StockInfo` 同步新增 `local_stock_first` 与 `stock_updated_at`。

### 2.5 前端

**C 端**（`frontend/src/shop/components/StockTag.tsx`，新建）：

| 情况 | 展示 |
|---|---|
| 精确库存 = 0 | `缺货`（红），禁止点击 |
| 精确库存 > 0 | `库存 N` |
| 估算库存 = -1 | `库存充足` |
| 估算库存 = 0 | `库存待确认` —— **不判缺货** |
| 估算库存 > 0 | `库存 N · X 分钟前` |

`isSoldOut()` 只在 `stock_exact && stock<=0` 时为真。这是刻意的：
**缓存过期导致把能卖的商品挡在门外，比让买家下单后自动退款更亏。**

**后台商品页**（`Goods.tsx`）：新增第三个供货方式选项、`取货顺序` 下拉
（卡密池优先 / 上游优先），并让「卡密与使用说明」与「货源路由」两块在混合模式下
**同时显示**；列表里混合商品同时提供「卡密池」与「货源管理」两个入口。

**后台商城页**（`ShopAdmin.tsx`）：库存列区分三种模式，混合/上游模式用 tooltip
给出「更新于 X 分钟前（具体时刻）」。

## 三、开发过程中发现并修掉的两个真实缺陷

### 缺陷 1：`fillCardStats` 漏掉混合商品

`backend/internal/service/goods.go` 里统计卡密数时只挑 `IsLocalStock()`，
混合商品的 `card_available` 永远是 0 —— 运营会以为「卡密没导进去」。

冒烟脚本第一时间抓到：`建商品时卡密已导入 -- card_available=0`，
而同一商品的 C 端库存却是 3（证明卡密确实在池子里）。
改为 `UsesCardPool()` 后恢复正常。

同类问题一并修掉：
- `handler_card.go` 的卡密导入拦截（否则混合商品无法导入卡密）；
- `RetryQuery` 改为按「订单有没有上游单号」判断，而不是按商品模式
  （混合模式可能这单吃池子、下单选上游，只有真正没有上游单号的才不能查单）。

### 缺陷 2：GORM 把显式的 `false` 吞成 `true`（最隐蔽）

`LocalStockFirst` 最初写成 `gorm:"not null;default:true"`。
结果：**显式传 `local_stock_first: false` 存进去是 `true`**，而且不报错。

复现（冒烟脚本场景 B）：请求体明确写了 `false`，商品快照里却是
`"local_stock_first":true`，日志显示 `混合模式：卡密池优先` ——
运营选了「上游优先」却永远得到「卡密池优先」。

原因：GORM 对带 `default` 标签的字段，会把零值当成「没填」，
插入时交给数据库默认值；`false` 正好是 bool 的零值。

修法：**让 DDL 默认值与零值一致**，应用层默认值由代码显式给出。

```go
// 改前：gorm:"not null;default:true"  → false 被吞
// 改后：
LocalStockFirst bool `gorm:"not null;default:false" json:"local_stock_first"`
// GoodsService.Create 里显式写 LocalStockFirst: true
```

这样「省略」和「false」落到同一个结果上，两条路径都正确。
AutoMigrate 会把已有库的列默认值一并改成 `false`（已在测试库与主库验证）。

两个缺陷都补了回归用例：
- `TestGoodsLocalStockFirstFalsePersists`（DB 层）
- `TestGoodsUpdateLocalStockFirstFalse`（Update 层）
- `TestGoodsInput_LocalStockFirstFalseBinds` / `..._DefaultsTrue`（绑定层）

## 六、遗留事项

1. **`MaxSupplyPrice` 是「每笔应付总额」上限，不是单价上限。**
   多件商品的成本红线若需按单价控制，需要另加 `MaxUnitPrice`。
   当前未实现 —— 用户确认的单件场景下总额上限已够用。
2. **上游库存缓存的新鲜度取决于 `stock_sync` 任务（每 2 分钟）。**
   若某货源长期同步失败，C 端会一直显示旧数字；后台诊断已给出
   「缓存可能已过期，点同步库存实时确认」的提示。
3. **混合模式暂未参与自动跟价 / 涨价告警**（那两项仍是独立待办）。
4. **退货卡密二次销售的风险由运营承担**（用户明确确认）：
   买家看过的卡密退回池子后可能已被使用，本迭代**未加** `view_count` 校验。
   `Goods.ReturnCardOnCancel` 默认仍为 `false`（不自动退回）。
