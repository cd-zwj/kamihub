## 一、一句话结论

把「付款到拿货」这段窗口里的**库存、资金、发货三方并发**全部收进数据库约束：
卡密预占消掉缺货窗口，单飞锁消掉重复发货，实付入账消掉三方金额不一致。
191 项后端测试全绿，前端 typecheck 与生产构建通过。

## 二、问题清单（按严重度）

| # | 现象 | 根因 | 影响 |
| --- | --- | --- | --- |
| 1 | 匿名买家付款成功，提示「商品暂时缺货」 | 付款窗口内卡密仍为 `available`，被别的买家买走 | 客诉 / 退款 / 口碑 |
| 2 | 提示「平台备货账户余额不足」 | `dispatchPaidOrder` 多入口并发，后到者撞「余额已被冻结」，失败原因写进 `auto_order_error` | 假故障，运营查上游一切正常 |
| 3 | 一次失败永久判死 | `order_id IS NULL && auto_order_error != ''` 是「不再尝试」闸门，网络抖动也终态 | 钱退余额，订单永远发不出 |
| 4 | 上游早没货，商城还挂「有货 5」 | 同步失败时保留旧库存，展示层无条件相信缓存 | 先收钱后退款 |
| 5 | 混合模式下单前完全不查库存 | 闸门只判 `IsLocalStock()`（仅 `StockModeLocal`），混合被跳过 | 付到成功才失败，静默无告警 |
| 6 | 页面显示 10 元、实际扣 9 元、收银台 10.1 元 | 报价走零售价、扣款走档位专价，两个入口不同源；网关再抬价 | 回调金额对不上 → 回 fail → 上游无限重试 |
| 7 | 老客户首次用匿名通道下单被拒「邮箱或安全密码不正确」 | `EnsureGuest` 按 `email` 取最早一行，正式账号挡住了匿名账号；`buyers.email` 无唯一索引 | 换个正确密码也永远进不去 |
| 8 | 失败订单在「我的订单」里看不到 | 订单归属回填在发货成功之后，失败单 `buyer_id` 为 NULL | 买家被引导到一个空列表 |

## 三、方案对照

| # | 方案 | 落地位置 |
| --- | --- | --- |
| 1 | 卡密第三态 `held(3)` + `held_by_request` + `hold_expires_at`；创建支付单即预占，占不满整批回滚 | `models/card.go`、`service/card.go`、`service/payment.go:CreatePay` |
| 2 | `payment_orders.auto_order_claim_at` 条件 UPDATE 抢锁（10 分钟租约，失败也释放） | `service/payment.go:claimAutoOrder` |
| 3 | 可重试错误识别 + 最多 3 次、间隔 2s，重试换幂等键 `{base}-rN` | `service/payment.go:autoOrderRetryable/dispatchPaidOrder` |
| 4 | `SupplyStockTTL = 15min` + `stock_stale` 标记 + 下单前实时询价 `RefreshStaleSupplyStock` | `service/listing.go`、`service/goods.go` |
| 5 | 统一闸门：池子 / 上游 / 混合三分支，上游按「全部自检失败或新鲜库存为 0」判死 | `service/listing.go:buyerQuote` |
| 6 | `QuoteFor(buyerID)` 三处同源；`amountAcceptable` 改「少付拒绝、多付放行」，按实付入账 | `service/shop_order.go`、`service/payment.go`、`api/handler_tier.go` |
| 7 | 匿名买家查询先按 `is_guest = true` 过滤，再单独判断是否正式账号 | `service/guest.go` |
| 8 | 订单归属在拿到 order 的瞬间回填，与发货结果无关 | `service/shop_order.go:Purchase` |

## 六、遗留与下次要盯的点

| # | 项 | 建议 |
| --- | --- | --- |
| 1 | `guest.go` 的同邮箱场景只有逻辑修正，**没有单测**（需要 `buyers` 复合场景造数） | 下批补 2 项：正式+匿名并存时匿名可下单、匿名密码错误仍拒绝 |
| 2 | `claimAutoOrder` 的并发互斥目前靠条件 UPDATE，未做「两个 goroutine 抢」的并发测试 | 可加 `-race` + 并行测试验证只有一路 `RowsAffected = 1` |
| 3 | 预占只在「会吃卡密池」的商品上生效（`UsesCardPool`），纯上游代发没有预占概念 | 上游侧只能靠「下单前实时询价 + 上游闸门」，属已知局限 |
| 4 | 预占 TTL 固定 = `PAY_ORDER_TTL + 10min` | 若支付单 TTL 可配得很大（>1h），需评估长期锁库存风险 |
| 5 | 网关抬价无上限放行 | 目前靠日志 `amountDriftWarn = 0.10` 告警；若出现 >1 元偏差应人工介入 |

## 七、回滚方案

1. **代码回滚**：`git revert` 本批次提交，或回退到上一 tag 重新构建
   （`docker compose up -d --build`）。
2. **数据无害**：新增列 / 新枚举值不会破坏旧二进制；旧版本会把 `held` 卡密
   显示为「未知」状态，但 `CountAvailable` 仍只数 `available`，不会超卖。
3. **回滚后必做**（避免卡密被永久锁死）：

```sql
-- 把残留预占全部退回可售
UPDATE card_stocks
SET status = 0, held_by_request = '', hold_expires_at = NULL, updated_at = now()
WHERE status = 3;
```

4. **预占残留检查**（回滚前后都可跑）：

```sql
SELECT goods_id, count(*) AS held,
       count(*) FILTER (WHERE hold_expires_at < now()) AS expired
FROM card_stocks WHERE status = 3 GROUP BY 1 ORDER BY 2 DESC;
```
